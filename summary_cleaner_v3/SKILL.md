## 一、这个功能做什么（先理解，再动手）

**一句话**：把一份序时账里的每张凭证，自动归类到 20 个标准业务桶之一，
并**顺手编出现金流量表**。

**输入**：序时账 Excel/CSV（至少要有 凭证号、科目、借方金额、贷方金额 四列）
**输出**：同一份序时账 + 新增「业务分类」「置信度」「现金流量项目」等列；
另附现金流量表、现金流相关凭证、待复核清单与统计摘要。

> **为什么要做业务分类？** 就是为了能一键编现金流量。
> 业务分类是第一步，现金流量表是它的下游产物——两步一次跑完。

**谁在判断**（3.0 架构：判断权全在模型，程序只做杂活）：

| 角色 | 负责什么 |
|---|---|
| **模型**（微调的中文语义模型 BGE-Large） | **18 个业务桶的判定**——读「科目组合 + 摘要」给概率 |
| **程序** | ① 读文件/认列名/写回结果（ETL）② 加载模型、批量推理 ③ 两条写死的机械规则 ④ **业务桶 → 现金流量项目** |
| **你（AI）** | 复核**中、低置信度**的判断，以及现金流待复核的少数条目——这是本 skill 的核心价值 |

> ⚠️ **3.0 相比旧版最关键的变化**：程序**不再给业务桶打分**。
> 旧版是"程序规则 20% + 模型 80%"融合打分，实测程序那 20% 在 2,000 张凭证里
> **一张都没改变过结果**，纯属负担，已整个删除。
> 现在 18 个业务桶 100% 由模型判定。
>
> 但**现金流是纯程序的**：它不猜业务，只做"业务桶 → 现金流量项目"的映射。
> 这两件事的边界不要混。

**置信度**（高 ≥80% / 中 50–80% / 低 <50%）＝ 模型对最终结果的概率。
**高置信度可以直接采信；中、低置信度的需要你复核。**

## 二、20 个业务桶（判断的唯一依据）

判断凭证属于哪类业务时，**只能从这 20 个桶里选**，不存在第 21 个：

```
职工薪酬  长期资产  存货采购  销售收入  借款筹资  政府补助  折旧摊销  利息收支
分红股利  生产制造  研发      投资本金  日常费用  员工借款  押金保证金  税费
单位往来  其他业务                        ← 模型判定的 18 个
资金内部往来  汇兑损益                     ← 程序写死的 2 个（模型没学过）
```

**为什么最后两个必须由程序写死**：这类凭证是**机械性**的（纯资金划转、
结汇），没有业务语义——技术报告明确规定「硬规则桶绝不进入训练数据」，
否则会污染模型分布。所以**模型没有能力输出它们**，只能由程序判定：

| 桶 | 判定条件 |
|---|---|
| 资金内部往来 | 一张凭证的**全部**一级科目都属于货币资金（库存现金/银行存款/其他货币资金） |
| 汇兑损益 | 含财务费用 + 无其他损益类科目 + 无黑名单科目 + 摘要含「汇兑/结汇/收汇」 |

每个桶的含义、锚定科目、边界规则（哪些容易搞错）见
**`assets/bucket_definitions.md`（必读）**。判断前先读它，别凭常识猜。

> ⚠️ 常见错误：把「管理费用」「销售费用」当桶名——它们是**科目**；
> 「费用报销」是旧桶名，现叫 **日常费用**。

## 四、第 1 步：模型自检

模型是 4 件交付物（约 622MB），放在 `<SKILL_DIR>/assets/model/`：

```
assets/model/
├── fine_tuned/                ← ① 微调后的 BGE 编码器（model.safetensors 约 620MB）
├── finance_classifier.pt      ← ② 分类头权重（约 1.1MB）
├── subject_to_index.json      ← ③ 科目索引（158 个科目开关）
└── index_to_bucket.json       ← ④ 桶索引（18 个桶）
```

**一条命令查就绪度**：

```cmd
venv\Scripts\python.exe -X utf8 cli.py status
```

输出是单行 JSON（前缀 `RESULT `），关注这几个字段：

| 字段 | 含义 | 不满足怎么办 |
|---|---|---|
| `model_ready` | 4 件交付物是否齐全 | `false` → 走下面「模型下载」 |
| `model_info.best_val_acc` | 模型验证准确率（当前 97.39%） | 偏低说明模型老旧，可提示用户 |
| `torch_installed` | torch 装没装 | `false` → 回第 0 步 |
| `cuda_available` | 有没有可用 GPU | 决定 `inference_device_will_be` |
| `bucket_count` | 桶总数（应为 **20**） | 不是 20 → 交付物版本不对，别继续 |

**模型缺失时的下载**（三选一）：

```cmd
:: ① 推荐：双击 download_model.bat（若项目里带了）
:: ② 命令行
venv\Scripts\python.exe -m modelscope download daijiaoshou/hajishou-V1.0 --local_dir nn\_storage
:: ③ 网络差：让用户去 https://www.modelscope.cn/models/daijiaoshou/hajishou-V1.0 手动下载 4 件，按上面目录放好
```

**模型没装也要继续**：程序会自动降级成"纯程序规则模式"，
照样能分类，只是精度略低（无模型打分）。这时要**明确告诉用户**：

> 「这次没有 AI 模型参与，只用程序规则打分，准确率会低一些。
> 结果里所有凭证的置信度都会偏低，建议全部人工过一遍。
> 想要更准的话，我可以帮你把模型装上（约 622MB）。」

## 五、第 2 步：字段配置

### 5.1 先跑 check（不跑模型、不写任何数据）

```cmd
venv\Scripts\python.exe -X utf8 cli.py check "用户给的序时账.xlsx"
```

输出 JSON 里看这几个字段：

| 字段 | 怎么看 |
|---|---|
| `rows` | 读进来多少行 |
| `detected_mapping` | 自动检测到的列名映射 |
| `preview` | 每个字段的 3 个样例值——**用它确认映射对不对** |
| `missing_required_cn` | 缺哪些必需字段 |
| `ok` | 必需字段齐不齐 |

**必需字段**：凭证号、一级科目、借方金额、贷方金额。
**选填字段**：摘要（强烈建议有，模型主要靠它）、科目明细/二级科目、制单人。

### 5.2 自动检测对不上时，你来生成映射

程序是**角色化匹配**（每个字段有专属列名 + 排除名单），能识别这些真实表头：

| 字段 | 会被识别为 |
|---|---|
| 凭证号 | 凭证号、凭证编号、凭证字号、voucher、单号 |
| 一级科目 | **科目**、一级科目、会计科目、科目编码、总账科目 |
| 科目明细 | 科目名称、二级科目、科目明细（**只精确匹配**，不会抢走「科目」） |
| 摘要 | 摘要、说明、备注、业务描述、description |
| 借方金额 | 借方金额、借方、借方发生额、debit（容忍「借方金额(元)」这类后缀） |
| 贷方金额 | 贷方金额、贷方、贷方发生额、credit |
| 制单人 | 制单人、制表人、记账人 |

**对不上时**：写一个映射 JSON，用 `--set` 传进去。例如用户的表头是
「单据编号 / 存货科目 / 事由 / 支出 / 收入」：

```json
{
  "voucher_no": "单据编号",
  "subject": "存货科目",
  "summary": "事由",
  "debit": "支出",
  "credit": "收入"
}
```

存成 `字段映射.json`（建议放在输出目录），再跑：

```cmd
venv\Scripts\python.exe -X utf8 cli.py check "序时账.xlsx" --set "字段映射.json"
```

**必须重跑 check 确认 `ok: true` 再进入下一步。**

## 六、第 3 步：执行清洗

```cmd
venv\Scripts\python.exe -X utf8 cli.py run "序时账.xlsx" --out "输出目录" --set "字段映射.json"
```

（没有 `--set` 就省略该参数；`--out` 省略则默认输出到序时账同级的「序时账清洗结果」文件夹。）

**这次会话会做 6 件事**：

| 阶段 | 做什么 | 说明 |
|---|---|---|
| 1. ETL | 读文件、认列名、抽出一凭证一条的模型输入 | 顺带处理红字凭证、千分位金额、空摘要等脏数据 |
| 2. 硬规则 | 预分配「资金内部往来」「汇兑损益」 | 这两类机械凭证模型没学过，只能程序判 |
| 3. 切割 + 模型打分 | 按「科目组合 + 摘要」分组，**每组只问模型一次** | 实测省 66% 的模型调用（1 万张：9992 次 → 3324 次） |
| 4. **编现金流** | 业务桶 → 现金流量项目，方向看货币资金借贷 | **纯程序**，不过模型、不过 AI |
| 5. 写回 | 把结论写回每一张凭证 | 保证同一凭证的所有分录行标签一致 |
| 6. 导出 | 生成结果文件 | 见下表 |

**输出文件**：

| 文件 | 给谁 | 用途 |
|---|---|---|
| `<文件名>_分类结果.xlsx` | **用户** | 原序时账 +「业务分类」+「置信度」+「现金流量项目」（仅货币资金行） |
| `<文件名>_现金流相关凭证.xlsx` | **用户** | 含货币资金科目的**整张**凭证，带现金流量项目 |
| `<文件名>_现金流量表.xlsx` | **用户** | 按项目聚合（经营/投资/筹资）+ 净增加额 |
| `<文件名>_待复核条目.xlsx` | **你（AI）** | 去重后的中/低置信度**条目**（按条目复核，比逐凭证省得多） |
| `<文件名>_待复核.xlsx` | **你（AI）** | 中/低置信度的**凭证**清单，含模型 Top1–Top3 与概率 |
| `<文件名>_现金流待复核.xlsx` | **你（AI）** | 现金流判不下来的条目 —— **只在有**时才生成 |
| `<文件名>_凭证明细.xlsx` | 追溯 | 每张凭证的判定来源（模型/硬规则）与模型概率 |

**跑完必须检查这几项**（run 输出 JSON 里的字段）：

| 字段 | 期望 | 不正常说明什么 |
|---|---|---|
| `ok` | `true` | false → 看 `error` |
| `coverage` | 接近 1.0 | 偏低说明有凭证没分到桶 |
| `unclassified` | `0` | 不为 0 → 有凭证丢了标签，别交付 |
| `hard_rule_hits` | 看情况 | 占比重很高说明这家公司资金划转多，属正常 |
| `confidence_dist` | 高占多数 | 低置信度占比过高 → 模型可能不适配这家公司 |
| `model_calls_saved` | 远大于 0 | 为 0 说明这份序时账摘要几乎不重复（正常，只是省不下调用） |
| `cashflow.money_vouchers` | 看情况 | 含货币资金的凭证数，一般占全部凭证的一半以上 |
| `cashflow.needs_review_rows` | 越小越好 | 不为 0 → **先看 `_现金流待复核.xlsx`**，再出正式现金流量表 |
| `cashflow.wash_rows` | 通常为 0 | 冲销分录（同行一借一贷），不进现金流量表，属正常 |

## 六之二、第 3 步之后：现金流量表（自动完成，不用额外命令）

`run` 已经顺手把现金流量表编好了，你**不需要**另跑命令。规则如下：

```
① 含「银行存款 / 库存现金 / 其他货币资金」的整张凭证才算现金流相关凭证
② 方向：货币资金借方 = 收现，贷方 = 付现
        （看在哪一方，不看正负号；借方负数 = 冲收现 ≠ 付现）
③ 项目：业务桶 → 候选范围 → 按方向筛出唯一一个
```

**编现金流不需要对方科目列，也不需要一级科目表。** 完整口径见
`reference/CASHFLOW_GUIDE.md`。

你要做的只有一件事：**若生成了 `<文件名>_现金流待复核.xlsx`，先把它处理掉**。
程序按纪律**不硬选**，只有两种情况会把它生成出来：

| 情况 | 含义 | 你怎么处理 |
|---|---|---|
| 同一方向下有多个候选 | 映射表被改出了二义性 | 正常不该出现；出现就修 `assets/cf/bucket_to_cf.json` |
| 桶映射为空但确实有货币资金收付 | 映射表漏配，或业务桶归属不对 | 看摘要判断：修映射表，或记一条"桶定义需补" |

**正常数据下这个文件不应该存在。** 它出现了就是信号，不要当成日常待办。

> 两个最容易混的桶：`借款筹资`（银行借款/融资）收现 → 取得借款收到的现金；
> `投资本金`（对外投资/收回投资/理财）收现 → 收回投资收到的现金。
> 映射表只做机械对应，不做语义翻译——股东出资若被归到 `投资本金`，
> 那是清洗阶段的归属问题，应去修桶定义/补训练数据。详见
> `reference/CASHFLOW_GUIDE.md` 第三节。

把结论追加到 `assets/AI_JUDGMENT_NOTES.md`。

> 交付时提醒用户：`_现金流量表.xlsx` 的末行是"现金及现金等价物净增加额"，
> 正式的现金流量表还需要**货币资金期初余额**（这一步暂未做）。

## 七、第 4 步：复核（本 skill 的核心价值）

**重点复核中、低置信度的凭证**——它们占比很小（实测高置信度占 95%+），
所以你的注意力要用在刀刃上。

### 7.1 先抽样（★ 用现成命令，别现场写脚本）

**高置信度也不能完全不看**，否则没有质量兜底。用 `sample` 命令随机抽几条核对：

```cmd
:: 抽 5 条高置信度的核对（固定随机种子，重跑拿到同一批，便于对照）
venv\Scripts\python.exe -X utf8 cli.py sample "输出目录\序时账_分类结果.xlsx" --confidence 高 --n 5

:: 抽中/低置信度的（这些是你要逐条复核的）
venv\Scripts\python.exe -X utf8 cli.py sample "...\序时账_分类结果.xlsx" --confidence 中 --n 20

:: 想覆盖全面一点：按业务桶分层抽（避免全落在一个大桶）
venv\Scripts\python.exe -X utf8 cli.py sample "...\序时账_分类结果.xlsx" --confidence 高 --n 12 --by-bucket
```

输出 JSON 里 `samples` 就是抽样结果，每条含 凭证号 / 业务分类 / 置信度 /
摘要 / 科目 / 金额 / 制单人。**注意 `--seed` 默认固定**，
所以同一文件重跑拿到同一批——这样你和用户讨论的是同一批凭证。

> 抽样规模建议：高置信度抽 5–10 条；中置信度全看；低置信度全看。

### 7.2 怎么判断

对每条待复核的「科目组合 + 摘要」，按这个顺序判断：

1. **先读 `assets/bucket_definitions.md`**，确认它该属于哪个桶；
2. **查 `reference/AI_REVIEW_GUIDE.md` 的跨桶决策表**——里面已沉淀了大量
   "这类业务归哪个桶"的硬规则（模具/委外/票据/手续费/系统维护费…），有明文就照办；
3. **查 `assets/AI_JUDGMENT_NOTES.md`**——你之前积累的词表与确认案例；
4. 三条都没有 → 自己判断，并说明依据。

**判断纪律**：

- **只能选 20 个桶里的**，不能造新桶；
- **拿不准不要硬猜**，标为"待人工确认"交给用户；
- 金额、日期、票号、凭证号对分类**无意义**，忽略它们，看业务语义。

### 7.3 复核结论怎么给用户

按「确认无误 / 建议改判 / 待人工确认」三类汇报，建议改判的要说清依据：

> 「800 张凭证里，796 张高置信度。我抽了 5 张核对，都对得上。
> 4 张中置信度的我逐条复核过：3 张没问题，1 张建议改判——凭证 记-00512
> 「系统维护费 2024.02-2025.01」，模型判成长期资产，但按规则"系统维护费"
> 应归**日常费用**（软件开发费才归长期资产）。」

### 7.4 改判怎么做（不做纠错累计）

**AI 可以给改判建议，但不需要、也不应该逐条去"教"程序。** 原因：

- 纠错累计是 1.0 时代（纯程序）留下的机制，那时只能靠用户逐条纠正；
- 现在主判断权在模型（80%），**如果出现成规模的错误，根子在模型与训练数据，
  逐条纠错是杯水车薪**；
- 本 skill 已经用 `assets/AI_JUDGMENT_NOTES.md` 做经验积累，
  再叠一套纠错累计是**重复动作**。

**所以请这样做**：

| 情况 | 怎么处理 |
|---|---|
| 零星几条判错 | 在汇报里列出「建议改判」，让用户在 `分类结果.xlsx` 里直接改「业务分类」列 |
| **同一类业务成批判错**（比如整个"委外加工"都错了） | **不要逐条纠**。告诉用户：这家公司的数据与模型现有训练数据偏差较大，需要**补充训练数据后重训模型**才能根治 |
| 用户明确纠正的个别案例 | 记进 `assets/AI_JUDGMENT_NOTES.md`（第二节），供你以后判断参考 |

> 用户改了 Excel 后，如果希望**程序**也学到，那需要走 Streamlit 纠错页
> （本项目另一个入口，不在本 skill 范围内）。本 skill 不提供纠错 CLI。

## 十、故障排查

| 现象 | 原因 | 怎么办 |
|---|---|---|
| `check` 报 `missing_required_cn` 有「一级科目」 | 表头命名特殊（如「存货科目」） | 生成映射 JSON 用 `--set` 传 |
| `run` 报「必需字段缺失」 | 没跑 `check` 确认映射 | 先 `check`，对不上就补 `--set` |
| `sample` 报「这不是分类结果文件」 | 传了原始序时账而不是结果 | 传 `run` 导出的 `<文件名>_分类结果.xlsx` |
| `coverage` 明显低于 1.0 | 有凭证没分到桶 | 看桶分布，排查科目是否缺失 |
| `cuda_available: false` 但用户有 N 卡 | torch 装成了 CPU 版 | 按第 0 步换 CUDA 版 torch |
| 模型加载报 `num_subjects` 不一致 | 交付物版本不匹配 | 重新下载 4 件交付物 |
| 报 `FileNotFoundError: 交付物①缺失` | 模型没下全 | 回第 1 步 |
| 报 `现金流映射表缺失` | `assets/cf/` 被删了 | 跑 `scripts/build_cf_maps.py` 重新生成 |
| `_现金流待复核.xlsx` 有内容 | 业务桶在该方向下有多个候选 | **正常**，逐条判断后写进 `AI_JUDGMENT_NOTES.md`；不要改程序去硬选 |
| 现金流结果整列是空的 | 序时账里没有「银行存款/库存现金」等货币资金科目 | 确认这是经营主体的序时账；没有货币资金就无所谓现金流 |
| 内存不足 / OOM | 凭证量极大 + 低配机器 | 拆分文件分批跑；或关掉其他程序 |
| 中文乱码 | Windows 控制台编码 | 命令前加 `-X utf8`（本手册已统一加） |

## 十二、给 AI 的最终提醒

1. **别跳过 `status`**。先知道模型在不在、走 CPU 还是 GPU，再决定怎么向用户交代耗时。
   **模型不齐就没法分类**（3.0 的 18 个业务桶全依赖模型，没有"纯程序降级模式"）。
2. **别跳过 `check`**。字段配错会让整份结果作废，而这一步只要几秒。
3. **交付前检查** `coverage` 接近 1.0、`unclassified` 为 0。不满足就别交付，先排查。
4. **复核用 `sample` 命令抽样**，不要现场写脚本：
   高置信度抽 5–10 条核对，中/低置信度逐条看。
5. **只认 20 个桶**，拿不准就交人工，**绝不硬猜**。
6. **成规模的错误不要逐条纠**——那是模型与训练数据的问题，
   应建议用户补充训练数据后重训；零星错误让用户直接改 Excel。
7. **每次都要更新 `assets/AI_JUDGMENT_NOTES.md`**——这是让这个 skill 越用越准的唯一途径。
8. **用户的序时账是敏感财务数据**：全流程本地运行，不要把数据发到任何外部服务。
