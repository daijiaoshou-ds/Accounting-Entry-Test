整套东西不是「让大模型读账」。它是一个判别式分类器：把「这张凭证是什么业务」建模成 24 选 1 的单选题，模型只输出概率分布，不给理由。全部判断力来自两路输入——摘要文本（语义）和科目组合（会计形态），金额数值、日期、制单人根本不进模型。

01输入层：一张凭证被拆成两个张量

序时账是行级的，模型是凭证级的，第一步是分组与提取。这一步在 extract_voucher_features()（nn/data.py:138）里一次向量化完成，训练和推理共用同一份代码——口径不一致会直接导致线上输入分布漂移。

1.1 摘要通道：把多行摘要拼成一句

同一凭证号下的所有非空摘要，先做空白压缩，再去重，然后用空格拼接，截断到 200 字符；tokenizer 那层再截到 64 个 token。

# nn/data.py:197-211（简化）
frame = frame.drop_duplicates(subset=["v", "t"])      # 同凭证内摘要去重
joined = frame.groupby("v")["t"].agg(" ".join)        # 空格拼接
summary_map = {v: t[:200] for v, t in joined.items()} # 字符级防御

为什么不是取首行摘要：多行凭证每行摘要可能不同（尤其一笔多科目的复杂凭证），只取首行会丢掉后面几行的业务线索。训练数据就是这么拼的，推理必须一致。

1.2 科目通道：每行按借贷方向生成一个令牌

每一行先判方向，再拼成 科目[借] / 科目[贷] 的形式，去重排序，最后映射成 187 维 one-hot。

规则判定为什么这样写
方向abs(借) > abs(贷) → 借，否则贷红字凭证（负数）必须靠绝对值判方向，否则 -826.97 > 0 为假，整行被跳过
零金额行借贷都为 0 → 丢弃没有金额的分录行不携带方向信息
科目归一剥二级后缀 → 查别名表研发费用—折旧费→研发费用，应交税金→应交税费
未知令牌词表里没有 → 该位保持 0不扩容词表（扩容会破坏已训练的权重位），只记进 unknown_subjects 报警
这里有个容易被忽略的取舍
科目通道是 one-hot 集合，不是序列。所以它丢掉了三样东西：金额大小、行的顺序、以及同一科目出现的次数——如果一张凭证两个不同二级科目都归一到了「银行存款」，开关仍然只有一位被置 1。它保留的是「借贷两侧一共动用了哪几个一级科目」这个组合形状。

02向量化：从 22 个 token 到 1024 个浮点数

摘要进入编码器这一段，是整个链路里唯一「重」的部分。用真实凭证走一遍：

真实凭证「2025年1月-记-0427号」的 tokenization 与编码路径

2.1 分词：字级 + WordPiece 续接

这是 BertTokenizer，中文按字切，连续数字用 WordPiece 切成最长匹配片段，未登录的后续片段带 ## 前缀。所以 2412 变成 241 + ##2，20 位发票号变成 9 个 token。NO 因为 do_lower_case=True 变成了 no。

这个细节有实际后果：长数字是 token 预算的黑洞。一句 36 字的摘要里，41% 的位置被发票号碎片占用，而 64 token 的上限是硬截断——摘要再长一点，真正的业务词就会被切掉。这也解释了为什么去重那一步敢用「数字归一化」（把数字全替换成 #）来判重：模型本来也没从数字里学到东西。

2.2 编码：24 层，每层在算什么

每一层的计算量（以 pad 到 64 个位置计）：

子层矩阵形状MACs / 层作用
Q/K/V 投影64×1024 × 1024×1024 ×3201 M把每个 token 映射成查询/键/值
多头注意力16 头 × 64×64 × 64 ×28.4 M让「发票」「入账」等词互相看见
注意力输出投影64×1024 × 1024×102467 M把多头结果并回 1024 维
FFN（1024→4096→1024）64×1024 × 1024×4096 ×2537 M逐位置非线性变换，GELU

单层约 813 M MACs，24 层合计约 19.5 G MACs ≈ 39 GFLOPs。而分类头只有 1088×256×2 + 256×24×2 ≈ 0.57 MFLOPs——占比 0.0015%。也就是说，99.998% 的算力花在「理解摘要」，结论的最后一跳几乎免费。

cl100k 之外的一个事实：padding 也在算
单条 predict() 固定 pad 到 64，22 个有效 token 的句子照样跑 64 个位置的前向——理论上有 65% 的浮点运算打在水漂上。批量接口 predict_batch_full() 用 padding=True（批内最长对齐）+ 按长度排序分批，把这个浪费压掉了，这也是它比逐条推理快 2.1 倍的原因之一。

2.3 为什么取 position 0

[CLS] 是 BERT 预训练时为「下一句预测」准备的占位符，它没有对应的输入词，所以在 24 层自注意力里可以自由地对整句做聚合。微调之后，分类损失会把它塑造成一个「整句业务语义的压缩表示」。

实测这一张凭证的 [CLS] 是 1024 维、L2 范数 9.859，前 6 维是：

[-0.189519, 0.000170, 0.070184, -0.230393, -0.071012, -0.049311]

单看这些数字没有意义——它们只有经过分类头、与 24 个桶的输出权重做内积之后才有含义。这也是这类模型不可解释的根源：中间表示不对应任何人类可读的概念。

03计算：两路特征怎么合并，又是怎么选出桶的

两路特征各自成向量后拼接，再由一个两层 MLP 输出 24 个 logits

3.1 科目开关那一跳：one-hot 输入让矩阵乘法退化成查表

subject_linear 是一个 187 → 64 的线性层，权重矩阵 W 形状 [64, 187]，偏置 b 是 64 维。因为输入是 one-hot（只有 2~3 位是 1），

y = W · x + b   # x 是 one-hot，除了少数几位全是 0
  = b + Σi∈开着的位 W[:, i]

也就是说，「算出科目向量」这件事在数学上等价于「把几个 64 维向量加起来」——没有非线性，没有交互项。我实测验证了这一点：

# fp32 权重，同时用 F.linear 和手工列求和
ONEHOT_EQ_COLSUM True    maxdiff 0.0e+00   # 记-0025 号
ONEHOT_EQ_COLSUM True    maxdiff 6.0e-08   # 记-0427 号

这个等价关系带来三条可推演的结论，它们不是代码里写的，而是结构决定的：

  • 科目组合是无序的。「应付账款[借]+银行存款[贷]」和「银行存款[借]+应付账款[贷]」得到的 64 维向量完全一样——因为加法可交换。方向信息只存在于令牌本身（[借]/[贷]），不存在于参与者与借贷侧的对应关系里。
  • 没有科目 = 只有偏置。187 位全 0 时 y = b，是一个固定的、与凭证无关的向量。所以「未知科目」不会让模型报错，只会让它退化成只靠摘要判断。
  • 组合表达能力被压在 64 维里。187 个科目的任意子集都要塞进 64 维，撞车是必然的；能区分多少，取决于训练时见过多少组合。
一个反直觉但重要的点
模型对科目的「理解」全部来自训练数据里这些 64 维向量被摆到哪里——它没有任何会计科目表、层级关系或借贷平衡的知识。你在账上看到「应交税费[借]」出现在采购凭证里，是因为训练数据里这种组合大量出现在「采购」桶下，而不是因为模型懂进项税。

3.2 拼接与分类头

两路向量直接 concat 成 1088 维。接着两次全连接：

层权重形状参数量输出
subject_linear[64, 187] + [64]12,03264 维科目向量

ReLU 之后的稀疏度值得一提：记-0427 号在 256 维隐层里只有 90 维被激活（35%）。大部分容量是闲置的——这也符合「24 类、2.5 万样本」这个任务规模。

3.3 从 logits 到概率：为什么概率总是 0.999

softmax 对 logit 差值极其敏感：exp(Δ)。记-0427 号的 top1 与 top2 logit 分别是 6.280 和 −10.509，差值 16.79，exp(16.79) ≈ 2.0×10⁷——所以校准后概率是 0.999963，几乎顶到 1。

这带来一个工程后果：原始概率不能直接拿来设阈值。任何「低于 0.8 就人工复核」的规则在这种饱和分布上都是废的（实测全量 2,216 张里有 2,186 张落在「高」档）。所以后面必须做温度缩放，这是下一节的事。

04全流程：模型不是唯一入口

4.0 版本的编排原则是：程序只负责「把输入准备好、把机械凭证摘出去、把结论写回去」，业务桶 100% 由模型给。唯一的程序判断是四类可枚举的机械凭证。

四类机械凭证在送模型之前就被摘走，其余凭证走模型

4.1 去重的三层判据

序时账里同一业务按月重复，摘要只差期间和金额。去重（dedup.py）分三层，成本递增：

层判据本次账本风险
L1 精确摘要与科目组合完全相同含在 L2 内零（输入相同，输出必相同）
L2 数字归一数字替换成 # 后相同合并 564 张零（只差数字，业务性质不变）
L3 相似度同组合内归一化相似度 ≥ 0.95合并 30 张低（靠阈值兜底）

「同科目组合」是硬前提而不是优化：支付当期税费 与 支付当期水费 去掉数字后相似度约 0.8，句式几乎一样，但前者科目是「应交税费 + 银行存款」、后者是「应付账款 + 银行存款」——业务性质完全不同。科目组合不同就绝不比较，这一条挡住了 L3 的主要误合并风险。

去重会放大错误（代表判错，全组跟错），所以有第二轮：代表概率低于 0.8 且组内多于一张时，成员各自重判并覆盖代表结论。detail 里的「组内张数」列就是给抽查用的。

5.4 为什么这张判「采购」判对了

把它拆成两个信号看，两路都在指向同一个答案：

  • 摘要：「发票入账」是采购侧的标准动作词；「某某科技」是供应商名（模型没见过这家公司，但见过大量「XX发票入账」的样本）。
  • 科目组合：「材料采购过渡 / 应交税费[进项] / 应付账款」是采购入账的典型三件套——进项税在借方、应付账款在贷方，这个形状在训练数据里几乎只出现在「采购」桶下。

正是因为两路信号一致，logit 差才会拉到 16.8，概率才那么极端。这一点在用「低置信 = 需要复核」的规则时很重要：低置信往往意味着两路信号打架，而不是模型算不出来。下面的 Case B 就是打架的样子。

6.1 红字凭证：方向判定必须用绝对值

顺带看一张红字凭证 2025年1月-记-0144号：

一级科目借方贷方判定若不取绝对值
研发费用−826.97—研发费用[借]被跳过
其他应付款—−826.97其他应付款[贷]被跳过

如果代码写成 debit > 0 判借，两个负数行都会被丢掉，科目组合变成空集，模型退化为只看摘要——这正是 data.py:130 用 abs(debit) > abs(credit) 的原因，注释里也留了实测记录（某次用户凭证只提取到「银行存款」一个科目）。

这张的结论是 单位往来 0.4288 / 费用 0.2174 / 销售 0.1319，校准后 0.3226，低置信。业务实质确实是往来款退回，所以 top1 方向对了，但概率只有 0.43——模型认得出「这是往来」，说不清「往来的是什么性质」。

更有意思的是脱敏带来的变化：原摘要里是客户简称 UL，把这两个字符换成「某客户」之后，top1 从「费用」翻成了「单位往来」。同一个业务、同样的科目，只改两个字，结论就变了。这是摘要字面敏感性的又一次现形——也正因如此，低置信的凭证必须进复核，不能只看 top1。

07后处理：24 个概率之后还有四道改写

顺序不可换：合并要在原概率空间相加，校准要在合并之后，回退用校准后概率

四步的顺序有严格理由，代码注释里写得很清楚：

  • 别名合并必须在原始概率空间做。合并桶（如「投资收益」→「投资」）的概率要相加，如果在 softmax 归一化之后才合并，概率会被二次归一化稀释。
  • 校准必须在合并之后。先校准再合并，等于对同一批概率做了两次不同的温度处理。
  • 回退判断必须用校准后概率。原始概率饱和在 0.99，0.45 这个阈值在原始空间里永远不触发。

温度 T=1.5 的选法也值得说：它不是按 NLL 最优选的（那是 T=4），而是按校准误差 ECE 选的。T ∈ {1, 1.2, 1.5, 2, 2.5, 3, 4} 的 ECE 分别是 0.023 / 0.021 / 0.011 / 0.023 / 0.057 / 0.095 / 0.196。用 T=4 时，高置信档覆盖只剩 46%，21.6% 的正常凭证被打成低置信；T=1.5 下高置信覆盖 89.2%、高档错误率 5.4%。

最终写回 7 列：业务分类、置信度（校准概率 0.8↑高 / 0.5↑中 / 其余低）、校准概率、模型概率、模型Top3、判定来源、后处理。另有 组内张数 标记哪些结论抄了组代表。

09训练侧：它凭什么学成这样

标签不是人工从零标的，而是「程序初判 → 按桶审核 → 金标准」的产物。审核界面是 buckets_v2 格式：桶 → 科目组合 → 摘要列表，审核方式是删除即标注——不属于该桶的节点直接删掉，不改桶名、不新增记录，剩下的天然属于该桶。

设计做法解决什么问题
摘要丢弃训练时随机把摘要换成空串，只留科目堵住「背摘要字面」的捷径。实测模型会把 发出商品--XX 整句记住，换成「交货」就崩
分层切分按桶 80/20，先切记录再展开 count同一条记录的所有重复样本必须进同一侧，否则验证集泄漏、准确率虚高
单桶上限每桶训练样本最多 12,000，等比缩放销售+采购占 56%，会先把验拉偏；上限只砍训练侧，验证集保持真实分布
双学习率编码器 1e-5 / 分类头 1e-3，warmup 10%预训练权重不能被大步长推离最优区域，头是随机初始化的，需要快学
best by val_acc每轮验证，只保存最优轮的 4 件交付物微调 1–3 轮就收敛，后面是过拟合

最近一次训练：BGE-large 全量微调，24,790 条样本，5 轮收敛，验证集准确率 97.07%，耗时 3.6 小时（GPU）。落盘 4 件交付物——微调编码器、分类头、科目索引、桶索引。加载时会逐项校验索引一致性：科目或桶的数量、名字对不上直接抛错，不允许带随机权重上线。

10.1 怎么用这些抓手做复核

按「校准概率升序」排，最不确定的排最前。一张一张看时，信息量最大的三列是：

  1. 模型Top3 —— 次优桶是谁。如果 top2 是「费用」而结论是「员工借支」，那 90% 是摘要里的「报销」和科目里的「冲备用金」打架，答案通常就在这两个里。
  2. 科目组合 —— 结构通道的完整输入。看到「其他应收款[贷]」就知道这张在冲备用金，不是新发生费用。
  3. 组内张数 —— 大于 1 说明结论是抄来的，抽查一张等于抽查一批。
