# 一、系统总览

## 1.1 双轨架构

系统由两条独立的判断链构成，最后加权融合：

```
                    ┌── 程序轨（V2.1 规则引擎）──→ 每个桶一个无界得分
一笔凭证 ───────────┤                                        ├─→ softmax + 融合 → 最终桶
（摘要 + 科目组合）  └── 模型轨（V3.0 分类模型）──→ 29 维概率 ─┘
```

**为什么保留程序轨**：模型有冷启动问题（新桶没有样本时完全不会判），程序用科目组合和
关键词兜底；程序有规则盲区（措辞没见过就漏），模型用语义兜底。两条链错的方式不一样，
融合后比任一条都稳。

> 注意：程序轨正在**有意收缩**。PMI 矩阵、自动词获取、纠错增强都是"模型判不准"年代的
> 补位机制，随着模型到位，它们的边际价值越来越低，且是"规则与统计混在一起"的复杂区。
> 目标形态是：**程序只保留硬规则（Step 0）与科目归一化，其余交给模型。**

## 1.2 四条执行路径

| 路径 | 触发条件 | 输出 | 置信度 |
|---|---|---|---|
| 硬规则预分配（Step 0） | 命中期末结转 / 资金内部往来 / 汇兑损益 / 员工借支 | 程序写死 | 高 |
| 纯程序降级 | 模型交付物缺失、OOM、加载失败 | 程序桶 | 低 |
| 未知科目退避 | 科目开关含未知令牌 | 程序桶 | 低 |
| 融合 | 其余全部 | 0.2·程序 + 0.8·模型 | 按模型概率分档 |

另有**评估模式**（`NN_PURE_MODEL_EVAL=1`，由 `start_eval.bat` 启动）：绕过融合、共享交集、
退避、父级回退，只用模型原始判断 + 温度校准。用来体检模型真实能力，不受程序兜底干扰。

# 二、业务桶设计

> 完整踩坑复盘见 `design/cleaner/bucket_design_principles.md`，
> 演化细节见 `design/cleaner/bucket_system_v10.md`。本章是它们的压缩与结论。

## 2.1 第一性原理

> **桶只回答一个问题：这笔钱是为哪件业务活动发生的。**
> 方向、含现、会计动作、利润影响、费用性质——全是派生维度，不进桶。

这句话否定了四种"顺手"的做法：

| 顺手做法 | 为什么不行 |
|---|---|
| 按会计科目分（管理费用桶） | 科目名不表达业务；等于硬编码，模型没有存在意义 |
| 按方向分（税费缴纳/返还） | 方向由借贷方向定，写进桶名等于二维压一维 |
| 按含现分（薪酬/计提薪酬） | 含不含现看有没有货币资金科目 |
| 按会计动作分（计提业务桶） | "计提"是记账时点，不是经济活动 |

## 2.2 解耦矩阵

| 维度 | 归属 | 载体 | 例子 |
|---|---|---|---|
| **经济活动** | **桶** | 32 桶 + 父级 | 销售、薪酬、费用·市场与销售 |
| 方向 | 派生 | 货币资金借贷 | 税费桶 + 借=缴纳 / 贷=返还 |
| 含现 | 派生 | 有无货币资金科目 | 薪酬 + 有现=发放 / 无现=计提 |
| 会计动作 | 派生 | 无现 + 贷应付类 = 计提 | 薪酬 + 计提标记 |
| 利润影响 | 派生 | 桶属性 + 对方科目 | 清偿负债 vs 确认费用 |
| 费用性质 | 派生 | 标签（刚性/弹性/项目性） | 房租=刚性，差旅=弹性 |
| 具体类别 | 派生 | 标签（差旅/广告/FOB） | 六类之下的明细 |
| 对手方 | 派生 | 标签（客户/供应商/员工/股东） | 关联交易识别 |
| 层级 | 结构 | 父桶 | 费用 → 六个子桶 |

**判断口诀**：能在一张凭证上读出来的（方向、含现）→ 不进桶；需要跨凭证统计才有意义的
（性质、对手方）→ 标签；决定这笔钱性质归属的 → 桶。

## 2.3 七次踩坑（浓缩）

| # | 坑 | 纠正 |
|---|---|---|
| 1 | 把"罗列"当"分类"（v4.1，53 桶） | 分类的价值在收敛，不在覆盖 |
| 2 | 把"会计科目"当"业务内容"（v7） | 同一笔电费，车间/门店/总部买的都是电 |
| 3 | 把"方向"写进桶名（v5） | 桶做归类，方向交给借贷 |
| 4 | 把"含现"写进桶（v6） | 同上，同一个病第二次犯 |
| 5 | 把"会计动作"当桶（v6 计提业务） | 计提是权责发生制的动作，不是生意 |
| 6 | 为现金流整齐而牺牲分录测试（研发并进费用） | 现金流允许多对一 |
| 7 | 部门口径残留（销售机构办公费归市场） | 办公就是办公，不管谁在用 |

## 2.4 五条铁律

1. **桶只归类经济活动**。方向、含现、会计动作、利润影响、费用性质全部解耦。
2. **按业务内容拆**，不按类别穷举、不按科目硬编码、不按部门划分。
3. **只有两种情况必须拆**：语义不明确（内部方差大）、不构成现金流单射。
4. **同一活动的正反两条线合并**（销售/退货、税费/缴纳返还、借款/取得偿还、投资/投出收回）；
   **平行活动不合并**（长期资产购建 vs 处置）。
5. **不为现金流整齐而合并**。多对一合法，牺牲分录测试的信息才是真损失。

**新桶四问**：是经济活动吗 → 是现有桶的反向吗 → 能靠"科目组合+摘要"判出来吗 →
不拆会语义混乱或不构成现金流单射吗。任何一步答"否"就停。

### 三条映射规则

1. **桶 + 方向查表，不需要科目裁判**。同一个桶落在两个项目上，由货币资金的借贷方向决定
   （税费缴纳 vs 返还、借款取得 vs 偿还）。
2. **多对一合法**。六个费用子桶 + 研发都映射到"支付其他与经营活动有关的现金"，
   这是设计允许的——桶的主要消费者还有分录测试，不能为了映射整齐而合并。
3. **混合到账按科目金额拆**。投资桶最典型：

| 凭证形态 | 现金流 |
|---|---|
| `交易性金融资产[贷] + 投资收益[贷] + 银行存款[借]` | 按两科目金额拆到两个项目 |
| `投资收益[贷] + 银行存款[借]`（纯分红） | 全额「取得投资收益」 |
| `交易性金融资产[贷] + 银行存款[借]`（纯赎回） | 全额「收回投资」 |

实现上通过 taxonomy 的 `cashflow_split` 字段声明触发科目与拆分科目。
混合到账若无法可靠拆分，落「待复核」并给出金额建议，**不做猜测性拆分**。

## 2.7 边界判例集

这些是复核过程中一条条吵出来的口径，**改桶或改数据之前先查这张表**。

| 情形 | 归桶 | 依据 |
|---|---|---|
| 库存商品/原材料 → 发出商品 | 成本结转 | 销售出库 |
| 发出商品/库存商品 → 主营业务成本 | 成本结转 | 商品成本结转是它自己的事 |
| 领料投产（原材料 → 生产成本/制造费用） | **生产制造** | 物料进入转化过程 |
| 完工入库（生产成本 → 产成品） | **生产制造** | 转化产出 |
| 委外加工发出/收回、制造费用结转生产成本 | **生产制造** | 委外生产、费用归集 |
| 采购入库后按部门分摊（贷应付暂估） | **生产制造** | 生产消耗；无制造/生产成本科目时落费用父级 |
| 车间水电汽 / 车间办公劳保 / 车间工资 / 车间折旧 | 费用·能源 / 费用·办公 / 薪酬 / 折旧摊销 | **成本中心 ≠ 经济业务** |
| 研发样品完工入库、研发部项目领用 | 研发 | 研发活动性质明确 |
| 进口关税、进口增值税缴款书 | **采购** | 进口环节税费随货走 |
| 进口设备增值税（含固定资产/在建科目） | 长期资产购建 | 随货走，货是资产 |
| 城建税/附加/印花/所得税/房产税/土地使用税 | 税费 | 国内税费独立成桶 |
| FOB / 报关 / 进出口运输 / 货代 / 运费（入主营业务成本） | **采购** | 买的是运输劳务，不按货物流向切 |
| FOB / 运费（入销售费用/管理费用） | 费用·市场 / 费用·办公 | 科目决定 |
| 模具/治具/工装：含固定资产 → 长期资产购建；其余 → 采购 | 按科目 | 模具是生产耗用，不是费用 |
| 分红代扣个税 | 利润分配 | "个税归薪酬"的分红环节例外 |
| 融资租赁租金（长期应付款[借]） | 借款 | 偿还融资负债，不是费用 |
| 承销费/保荐费/评级费/发行登记费 | 筹资费用 | 纯手续费类 |
| 定存：只计提利息 | 存款利息 | 单一动作 |
| 定存：到期/赎回（含本金） | 投资 | 有本金收付 |
| 银行承兑/贴现 | 利息支出 | 融资成本 |
| 汇票到期：`应收票据[贷]+银行存款[借]` | 销售 | 收回货款 |
| 汇票到期：`应付票据[借]+银行存款[贷]` | 采购 | **付**货款（方向是判据） |
| 平台/第三方手续费（支付宝、财付通、境外月费） | 结算手续费 | 桶名已从"银行手续费"改名 |
| 报销单里夹带手续费 | 费用（招待→治理、差旅→办公） | 主事件是报销 |
| 回款 + 银行手续费复合凭证 | 销售 | 主事件是收货款 |
| 费用父级 | 允许宽松输出 | 分不清本身就是信息，不强制"≥2 类才许输出" |

# 三、程序侧（V2.1 规则引擎）

## 3.1 得分公式

$$\text{Score}(b) = \lambda_{struct}\cdot(\mathbf{v}\cdot\mathbf{w}') + \max(b_{kw}, b_{auto}) + \text{clamp}(s,\pm0.05) + d + e$$

| 分量 | 含义 | 来源 |
|---|---|---|
| $\lambda_{struct}\cdot(\mathbf{v}\cdot\mathbf{w}')$ | PMI 相关性 × 桶偏好传播 | 统计 |
| $\max(b,c)$ | 手工词与自动词取最强（同词不重复加分） | 经验 + 统计 |
| $\text{clamp}(s,\pm0.05)$ | 金额对数正态偏离惩罚 | 统计 |
| $d$ | 人类纠错 → 桶顺位加分 | 反馈 |
| $e$ | 制单人（模块会计）偏好 | 组织 |

关键常数：`LAMBDA_STRUCT=1.67`、单桶关键词上限 2.0、金额上限 0.05、
`SUBJECT_DETAIL_KEYWORD_DECAY=0.6`、`TAX_DECAY=0.5`、制单人 ±0.5。

## 3.2 Step 0 硬规则

在打分之前按凭证号或科目形态直接定桶，置信度=高，不参与融合：

| 规则 | 判据 | 桶 |
|---|---|---|
| 0a | 凭证号在"结转损益"清单 | 期末结转 |
| 0b | 一级科目全为货币资金（银行存款/库存现金/其他货币资金互转） | 资金内部往来 |
| 0c | 期末调汇（外币科目 + 财务费用-汇兑损益） | 汇兑损益 |
| 0d | 员工借款/还款（其他应收款 + 员工姓名） | 员工借支 |

## 3.3 程序侧消融与精简档（2026-11-09）

**问题**：PMI 矩阵、自动词、纠错、制单人这四套机制，在今天（模型准确率 94%、置信度可用）
还有多少分量？

**方法**：不改生产代码，运行时 monkeypatch 逐个关掉分量，对比最终桶
（`_dev/scripts/ablation_program.py`）。样本：真实账 8,000 行 / 1,453 凭证。

| 模式 | 程序原生桶变化 | **最终融合桶变化** |
|---|---:|---:|
| 关结构分（PMI） | — | 0 |
| 关自动词 | — | 0 |
| 关纠错 / 制单人 | — | 0（两者默认就没传值，非空率 0%） |
| **全关（只剩锚定+关键词）** | **20.6%** | **0.0%** |

更进一步：**融合结果与"纯模型"（`NN_PURE_MODEL_EVAL`）在 1,453 张凭证上 0 差异**。

**原因**：模型权重 0.8，且模型 top1 概率通常 >0.95。程序要翻盘需要
`0.2·P_prog > 0.8·(P_nn_top − P_nn_次优)`，在饱和区几乎不可能。程序只可能在
模型犹豫（P_nn < 0.6）时才起作用——那正是低置信、本来就该人工复核的样本。

**落地**：`config.SCORER_PROFILE`（默认 `lean`，env `SUMMARY_CLEANER_SCORER=full` 可复原）。

| 档 | 保留 | 关掉 |
|---|---|---|
| **lean（默认）** | 科目锚定权重、手工关键词、金额特征、Step 0 硬规则 | PMI 传播、自动词、纠错顺位、制单人 |

全量 64,255 行 / 11,456 凭证实测：

| 档 | 耗时 | 与 full 的差异 |
|---|---:|---:|
| full | 93.1s | — |
| **lean** | **77.3s（-17%）** | **0 处** |

lean 还额外跳过了「自动词学习」整块（`session_wl.update` + 哈希词频落盘，
约 1.5s / 6,000 行）——它只更新学习状态，不参与当次决策。

**两点要说清楚**：

1. **17% 不是大头**。砍完还剩 77s，按 profiler 拆分（6,000 行样本）：
   模型推理 32%（`predict_batch_full`）、打分 30%（`Scorer.score`，主要是逐桶
   `Series.reindex`）、科目提取 18%（`extract_subjects_from_group`，**每张凭证被调用两次**）、
   训练数据导出 10%、其余为结果组装。真正的加速要靠**把打分改成矩阵运算**
   （`V @ W.T` 一次算出所有桶）和**科目只提取一次**，不是删模块。
2. **这本账在训练集里**，模型 97% 高置信。真正陌生的账上程序的作用会显现，
   所以 `full` 档保留、不删代码；等有陌生账复测后再决定物理删除。

| 情形 | 行为 |
|---|---|
| 模型交付物缺失 / 加载失败 / OOM | 纯程序，置信度=低 |
| 科目开关含未知令牌 | 程序 100%，置信度=低 |
| 程序首选桶不在模型输出集 | 退避程序 100%（防桶集漂移静默丢票） |

# 四、模型侧（V3.0）

## 4.1 架构

```
摘要整句 ──→ BGE encoder ──→ [CLS] 向量（large:1024 / base:768）
科目开关(176 维 multi-hot) ──→ Linear(176→64) ──→ 64 维
                    concat ──→ Linear(1088→256) → ReLU → Dropout(0.1) → Linear(256→29)
                    ──→ logits ──→ softmax ──→ 温度校准 ──→ 融合
```

- 编码器：`BAAI/bge-large-zh-v1.5`（生产）/ `bge-base-zh-v1.5`（实验）
- 策略：全量微调（编码器 + 分类头），batch 4，maxlen 64，8 epochs
- 交付 4 件套：`fine_tuned/`、`finance_classifier.pt`、`index_to_bucket.json`（29 维）、
  `subject_to_index.json`（176 维）

## 4.2 为什么是分类，不是向量检索

早期（v2）用 Triplet Loss 学 embedding + 最近邻聚类；v3 起改为监督分类。区别：

| | 向量检索 | 分类（现行） |
|---|---|---|
| 判断方式 | 算相似度找最近样本 | 29 路 softmax 直接学边界 |
| 谁决定标签 | 邻居投票 | 模型自己输出 |
| 能否表达口径 | 不能（"费用父级宽松"没法编码） | 能（从样本里学） |
| 新增桶 | 加样本即可，无需重训 | 必须重训 |

代价是"加桶要重训"，收益是边界更清晰、置信度可用。对 29 个语义高度重叠的桶，后者更合适。

## 4.3 科目归一化（模型之前的前置步骤）

顺序固定：**读原始一级科目 → 剥后缀 → 查别名表 → 拼科目组合 → 送模型**。

| 步骤 | 函数 | 做什么 |
|---|---|---|
| 剥后缀 | `split_suffix` | 按 `— - – / · （）` 等分隔符机械切主干，只留一级科目 |
| 查别名 | `alias_of` | 映射表 `{"match": [...], "to": "标准科目"}`，`*` 作通配 |
| 组合 | — | `f"{标准科目}[借/贷]"` multi-hot |

**为什么必须在拼组合之前做**：模型的输入是"科目开关"，不是文本。`研发费用—材料费`
和 `研发费用` 在词表里是两个维度，前者没学过就等于没信号。

实测效果（一本陌生账，2,104 条去重记录）：

| 指标 | 改前 | 改后 |
|---|---:|---:|
| 未知科目种类 | 131 | **19** |
| 未知次数 | 1,631 | **400** |
| 含未知科目的凭证 | 57.7% | **17.7%** |
| 排除「万和」这类客户名当科目后 | — | **2.1%** |

安全阀：归一化后的名字不在词表、而原名在 → 保留原名（绝不把认识的开关改坏）。
方向缺口兜底：词表里同名科目只有另一方向时，用那一方向的开关。

维护：`_dev/scripts/list_unknown_subjects.py` 按频次列出未知科目，贴进映射表即可，
**不用重训**。骨架由 `_dev/scripts/build_subject_alias_table.py` 生成（102 条标准科目）。

## 4.4 训练数据管线

```
分类结果 → 按凭证号分组 → 记录级去重（精确 + 相似）→ count 计数 → 金标准 training_data.json
```

要点：

| 项 | 做法 | 原因 |
|---|---|---|
| 去重粒度 | `(归一化摘要, 排序后的科目组合)` | 同摘要同科目 = 同一样本，count 累加 |
| count 展开上限 | `MAX_COUNT_EXPAND = 20` | 防单条高频样本膨胀失控 |
| 划分 | 先按**记录**分层 80/20，再各自展开 | 先展开再切会让同一条记录的展开样本同时进训练和验证 → val_acc 虚高 |
| 头部缩放 | 单桶有效样本上限 12,000，**只作用于训练侧** | 头部占 57.8%，缩放后 46.4%；**不删记录**，按 12,000/现有 等比缩放 |
| 验证集 | 保持真实分布，不缩放 | 配平后测不出真实表现 |
| 跳过桶 | 未分类 / 无法分类 / 期末结转 / 资金内部往来 / 汇兑损益 | 机械凭证或硬规则 |

实测（v10.2）：训练 40,680 / 验证 12,649，头部占比训练侧 46.7%、验证侧 55.9%。

## 4.5 训练方法（本轮新增）

### 摘要丢弃（`--summary-dropout 0.3`）

训练时按概率把摘要置空（只留 `[CLS]/[SEP]`），逼模型学"科目组合 → 桶"而不是背摘要字面。

动机见 §6.4：模型一度对 `发出商品[借]+库存商品[贷]`（金标准里 3,874 count 100% 成本结转）
这个组合判成采购，因为它只记住了"发出商品--XXX客户"这个句式。

### 其他参数

| 参数 | 值 | 依据 |
|---|---|---|
| encoder | bge-large-zh-v1.5 | 与 v10 保持一致才可比 |
| epochs / patience | **5 / 2** | v10.2 最佳在第 4 轮，第 5 轮起 val_loss 一路上涨，后 4 轮白跑 3 小时 |
| batch / maxlen | 4 / 64 | 8GB 显存约束；maxlen 64（中位摘要 46 字，90 分位 164 字会被截断，实测拉长收益不大） |
| 损失 | CrossEntropy | |

# 五、融合与置信度

## 5.1 程序概率化

程序输出是无界得分，先 clamp 再 softmax：

$$P_{prog}(b) = \frac{\exp(\text{clamp}(S_{prog}(b),-5,5)/T)}{\sum_{b'\in shared}\exp(\text{clamp}(S_{prog}(b'),-5,5)/T)},\quad T=2.5$$

clamp 的必要性：程序真实得分上限约 5–6（关键词 2.0 + 自动词 2.0 + 纠错 2.5 + 制单人 0.5）。
曾出现某凭证 15 分 → $e^{15/2.5}=403$ → softmax ≈ 1，0.2 的权重仍能翻转模型判断。

## 5.2 融合公式

$$P_{final}(b) = 0.2\cdot P_{prog}(b) + 0.8\cdot P_{nn}(b),\qquad bucket^*=\arg\max_b P_{final}(b)$$

约束：

- 只在**两侧共有的桶**上融合；程序首选桶不在模型输出集 → 退避程序 100%
- 硬规则预分配凭证不参与融合
- 空摘要凭证不参与融合
- 别名重定向（`merge_alias_probs`）**必须在融合之前**，否则模型票落在旧桶名上会被交集静默丢弃

## 5.3 温度校准（2026-11 重要修正）

模型 8 轮训练后概率饱和：验证集 top1 均值 0.992、>0.99 占 95.4%。因此必须做温度缩放
（`softmax(log(p)/T)` 与 `softmax(z/T)` 等价，无需模型暴露 logits）。

**当前 T = 1.5**，依据从 NLL 改为 **ECE（校准误差）**：

| T | 高置信覆盖 | 高置信档错误率 | 低置信占比 | ECE |
|---:|---:|---:|---:|---:|
| 1.0 | 94.0% | 6.4% | 0.9% | 0.023 |
| **1.5** | 89.2% | 5.4% | 2.2% | **0.011** |
| 2.0 | 84.0% | 4.1% | 6.0% | 0.023 |
| 4.0（旧值） | 46.1% | 2.5% | 21.6% | 0.196 |

旧值 T=4 是按 NLL 最小化选的。**NLL 被"自信地判错"的少数样本绑架**（4% 的错判贡献 93%
的 loss），压平它们降 NLL 最快，代价是把 94% 判对的也一起压平——高置信档只剩 46% 覆盖，
21.6% 的正常凭证被打成低置信。T=1.5 才是校准最好的点。

父级回退阈值同步从 0.6 调到 **0.45**（T=1.5 下对应约 3% 回退率，与原设计意图一致）。

## 5.4 置信度分档

| 档 | 条件 | 用途 |
|---|---|---|
| 高 | $P_{nn}(bucket^*)\ge 0.80$ | 可直接采信 |
| 中 | $0.50 \le P < 0.80$ | 建议抽查 |
| 低 | $P < 0.50$ | 必须人工复核 |

硬规则预分配=高；未知科目退避=低；融合成功按 $P_{nn}$ 分档。

> **风险提示（2026-11 发现）**：降 T 会把"系统性错误"从低置信推到高置信。
> 曾出现某类凭证（`交货` 措辞）673 count 判错、降 T 后有 636 count 变成高置信。
> 结论：**高置信档的质量取决于最大的那一个系统性错误，而不取决于 T**。
> 解决方式是补样本 / 改训练方法，不是把 T 调回去（T=4 等于用 40% 的低置信掩盖 6% 的错误）。

## 6.4 摘要丢弃实验（最重要的方法论收获）

**现象**：`交货 - C000425,深圳麦哲科技` 被判采购，而 `发出商品[借]+库存商品[贷]`
在金标准里 3,874 count **100% 是成本结转**。

**探针**（固定同一科目组合，只改摘要）：

| 摘要 | 判断 |
|---|---|
| `发出商品--某客户` | 成本结转 1.000 ✅ |
| `结转本月发出商品` | 成本结转 1.000 ✅ |
| `交货` | 采购 1.000 ❌ |
| 中性文本「本月合计」 | 采购 0.99 ❌ |

**结论：模型认的是"发出商品"这四个字，不是科目组合。** 一旦摘要没有提示词，就掉回先验
（采购是最大桶），组合完全拉不回来。

**做法**：训练时按概率把摘要置空，堵死"背摘要"这条捷径。

| 测试集 | 对照（0） | 丢弃 0.3 |
|---|---:|---:|
| A 交货措辞（120 条，训练集从未出现的说法） | 26.7% | **99.2%** |
| B 中性文本（846 条，只给科目组合） | 13.1% | **32.2%** |
| C 常规验证（2,000 条） | 93.8% | 94.0% |

B 组关键桶（只给组合不给摘要）：

| 桶 | 对照 | 丢弃 0.3 |
|---|---:|---:|
| 成本结转 | **0/30** | **28/30** |
| 生产制造 | 6/30 | **30/30** |
| 费用·办公 | 0/30 | 2/30 |

**丢弃率扫描**：

| 丢弃率 | A | B | B·成本结转 | B·生产制造 | C | val_acc |
|---:|---:|---:|---:|---:|---:|---:|
| 0 | 26.7% | 13.1% | 0/30 | 6/30 | 93.8% | 93.87% |
| 0.2 | 98.3% | 24.5% | **0/30** | 20/30 | 94.2% | 93.91% |
| **0.3** | **99.2%** | 32.2% | 28/30 | 30/30 | 94.0% | 93.89% |
| 0.4 | 98.3% | **37.1%** | 28/30 | 30/30 | 94.2% | 93.95% |

**读法**：0.2 是坑——措辞救回来了但组合仍是 0/30，它靠残留文字线索在猜。
**0.3 是拐点**（组合真正学会），0.3 与 0.4 实质打平，取 0.3（干预更小、A 组略好）。
常规准确率三者都在 94% 左右，**丢弃没有代价**；唯一代价是收敛慢半拍。

## 6.5 指标口径的坑

`per_bucket_accuracy` 是**按 count 展开后的样本级**准确率。一条 count=12 的记录，
在验证集里就是 12 条一模一样的样本。

投资桶 52 条验证样本里有 12 条是同一条记录（`收中国证券登记结算…派发红利代扣个税`），
它一错，投资就掉 23 个百分点——**记录级实际是 92.5%**。

**规则：以后看分桶指标，必须同时看样本级和记录级。** 小桶（<20 条验证样本）的单点准确率
没有统计意义，要看混淆矩阵；v10 那批"100%"的桶只有 5–6 条验证样本，不可比。

# 七、架构改造（2026-11）

## 7.1 单一数据源

`config.BUCKET_REGISTRY` 不再手写，改为从 `assets/bucket_taxonomy_v10.json` 派生
（`bucket_registry_v10.py`）：

| 机制 | 作用 |
|---|---|
| `LEGACY_ALIAS` | 旧桶名 → 新桶名（20 条），含"生产制造→自己"（否则新桶被历史别名重定向掉） |
| `SPREAD` | 一对多（5 条），如"材料"拆到多个费用子桶 |
| 继承 v9 人工科目权重 | 派生时合并旧 `BUCKET_REGISTRY` 的 `subject_weights` |
| `SUMMARY_CLEANER_BUCKETS=v9` | 一键回退旧 20 桶；`_dev/rollback_to_v9.py` |

好处：桶表只有一处真相，改 taxonomy 后注册表、关键词表、现金流映射、训练跳过集全部跟着走。
代价：taxonomy 的字段必须有约束（`code` 唯一、`train` 标记真正被读、`parent` 指向存在的桶）。

> **踩过的坑**：`train` 字段曾经全代码无人读，12 个桶标着 `train=false` 却都在训练集里
> （含长期资产购建、借款等主力桶）。已改为 `DEFAULT_SKIP_BUCKETS` 直接读 taxonomy。

## 7.2 别名重定向

模型输出的是重训时的桶名。桶改名后（如"银行手续费→结算手续费"），
旧模型仍输出旧名，靠 `merge_alias_probs` 在**融合之前**把概率并入新名。

`index_to_bucket.json` **绝不能手工改**——那是模型的输出映射，重训后才会变。

## 7.3 I/O 与数据格式（2026-11-09）

| 项 | 改前 | 改后 |
|---|---|---|
| xlsx 读取 | openpyxl（10.3s / 64k 行） | **calamine（Rust）2.5s**，失败回退 openpyxl |
| .xls | **读不了**（openpyxl 不支持） | 可读 |
| 中文 CSV（GBK） | `UnicodeDecodeError` | utf-8-sig → utf-8 → gb18030 回退 |
| 输出 | 一律 openpyxl | ≤50 万行 xlsx（xlsxwriter）；>50 万行 **CSV** |

为什么是 50 万：Excel 单表硬上限 1,048,576 行，留 4 倍余量避免用户二次加工后溢出。
硬写 xlsx 会静默丢行。

格式实测（64,255 行 → 200 万行推算）：

| 格式 | 写 | 读 | 体积 |
|---|---:|---:|---:|
| Feather | 2.1s | — | 4.2MB |
| **Parquet** | 6.6s | 3.6s | **1.2MB** |
| CSV | 10.7s | 5.9s | 18.1MB |
| SQLite | 11.8s | 11.6s | 20.3MB |
| xlsx | **467s** | 270s | 7.2MB |

内部落盘用 Parquet（小 15 倍、保留科目编码前导零）。**输入侧不做预转换**——
一份文件一次会话只读一遍，转换是纯支出。

## 7.4 性能画像

真实账（64,255 行 / 11,328 凭证 / 2,562 去重记录）端到端 **97s**：

| 阶段 | 耗时 | 占比 |
|---|---:|---:|
| 模型推理（2,562 条） | 6–25s | 6–26% |
| 程序打分（11,328 凭证） | 11.9s | 12% |
| 导出训练数据（含相似去重） | 13.1s | 13% |
| **逐行组装/分组/融合** | **50–60s** | **50–60%** |
| 读表 | 1.6s | 2% |

**关键认识：去重是 25:1（行 → 凭证 5.7:1，凭证 → 记录 4.4:1），所以模型调用量远小于行数。**
200 万行对应 8–22 万次模型调用（3–8 分钟），而逐行 Python 处理要 40–45 分钟。

## 7.5 Rust 决策（结论：不重写）

| 项 | 实测/推算 |
|---|---|
| 引擎（读+写+逐行）占 200 万行总时长 | **约 85%** |
| Rust 理论上限 | 4–6× |
| 但纯 pip 改动（calamine + CSV） | 先拿 1.3–1.4× |
| **真正该先做的是向量化** | 50–60s 花在 `iterrows`/`groupby` 逐组/dict 组装 |

`calamine` 的 91% 时间花在"把 Rust 对象转成 Python 对象"（解析本身 0.10s，转对象 0.96s）。
**"原生 Rust 更快"只在全程不落地 Python 对象时成立**，即 PyO3 扩展形态：
Rust 负责解析 → 归一化 → 指纹 → 聚合 → 写盘，只把结果交回 Python。

触发条件（写死，别凭感觉）：向量化之后 ETL 仍 >50%，或需要单进程 >500 万行。

## 7.6 缓存（设计完成，未实施）

设想：把「摘要 + 科目组合」当指纹缓存结果，命中就不走模型。

实测结论：

| 归一化层级 | 跨账命中 | 同分布拆半 | 命中后标签一致 |
|---|---:|---:|---:|
| L0 原样 | **0.00%** | 0.00% | — |
| L1 数字掩码 | 0.00% | 0.44% | 0% |
| L2 +去括号+首句+实体 | 0.00% | 1.97% | 62.8% |

**跨公司命中率几乎为零**——摘要高度公司化（贷款期限、报关单号、客户名），而且账内
本来就去重了。正确作用域是**同一客户逐月重跑**。

设计（不需要客户 ID）：键 = 归一化摘要 + 科目组合；存 `键 → {标签: 票数}`，
同键多标签即"桶分错了"（不命中）；键里带模型/桶表/别名表版本；人工复核回写。

## 9.2 标注冲突检查（`_dev/scripts/check_label_conflicts.py`）

| 层 | 键 | 冲突 | 说明 |
|---|---|---:|---|
| L0 精确 | 去空白摘要 + 科目组合 | **0 组** | 同键不同桶一定是错标 |

那轮修正（19 条 / 80 count）。

> **教训**：业务动词（"到期""回款""结算"）本身不含方向，规则必须看借贷方向。
> 一条"含汇票到期且桶=采购 → 销售"的规则差点把 552 count 的**付**货款挪走，
> 因为 `应付票据[借]+银行存款[贷]` 也含"汇票到期"。预演救回来了。

## 9.3 三组评测（`_dev/scripts/eval_ood_wording.py`）
