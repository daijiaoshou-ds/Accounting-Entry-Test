# 一、系统总览

## 1.1 单一编排

判断链只有一条：**程序做确定性工作，模型做语义判定，两者不投票、不加权。**

```
                        ┌─ 读表 + 字段映射
一笔凭证 ────────────────┼─ 科目归一化 + 拼组合 ──→ 187 维开关
（摘要 + 科目组合）      └─ 四类机械凭证直接定桶 ──→ 终局（置信度=高）
                                        │
                                        └─ 其余交给模型 ──→ 24 类概率 ──→ 温度校准 ──→ 终局
```

**为什么不是双轨融合**：程序对同一份摘要的另一种读法，并没有比模型更多的信息。
实测程序打分全开与全关，11,456 张凭证的最终桶差异 **0 条**；与"纯模型"比只差 3 张
（0.03%，全在费用父级与子桶之间，随子桶合并已消失）。规则唯一能翻盘的情形是模型本身
犹豫——而那正是该进复核清单的样本。详见 §3.4。

**程序不碰的事**：不给桶打分、不做关键词/金额/制单人偏置、不与模型结果融合、
不从人工纠错里学权重。人工结论进金标准、经重训回灌模型，这是唯一的学习通路。

## 1.2 三种执行路径

| 路径 | 触发条件 | 输出 | 置信度 |
|---|---|---|---|
| 硬约束 | 命中期末结转 / 资金内部往来 / 汇兑损益 / 员工借支 | 程序写死 | 高 |
| 模型判定 | 其余全部（含含未知科目的凭证） | 模型 top1 | 按校准概率分档 |
| 模型缺失 | 交付物缺失 / 加载失败 / OOM | 直接报错，不出半成品 | — |

模型缺失**不降级到纯程序**：程序已经没有判定能力，输出"纯规则"结果等于乱判。

未知科目也不降级、不降置信度——模型仍能按摘要判断，只在明细里标出并汇总成清单，
作为"该维护别名表了"的信号（§3.3）。

## 1.3 一份序时账传进来会发生什么

四个阶段。数字取自全年账（64,255 行 / 11,456 凭证 / GPU），括号内是 `case/序时账1.xlsx`
（11,604 行 / 2,216 凭证）的量级。

### 阶段 A：上传与预览（约 2 秒，不加载模型）

```
用户拖入 xlsx/csv
   ↓  read_table()：xlsx/xls/ods → calamine（Rust）；csv 按 utf-8-sig → utf-8 → gb18030 回退
   ↓  行数校验（>50 万行提示改 CSV）        DataFrame（64,255 × 27）
   ↓  auto_detect_columns()：按表头别名匹配 7 个字段
   ↓  未知科目扫描：归一化 → 查 187 个开关（不碰模型）
返回：列名 + 建议映射 + 前 20 行预览 + 未知科目清单
```

| 动作 | 做什么 | 耗时 |
|---|---|---:|
| 读表 | calamine 解析，比 openpyxl 快 4 倍 | 2.0s |
| 列识别 | 凭证号/摘要/一级科目/科目名称/借贷金额，按别名打分取最高 | ~0 |
| 未知科目扫描 | 归一化后查开关表，分出 `alias_candidate` / `need_training` / `direction` | 0.05s |

**这一步就能拿到未知科目清单**，用户可以在跑账之前先补别名表。

**实例（列识别）**——本账 27 列里，6 个关键字段全部按别名命中，另有日期/币种/原币金额
作为辅助信息一并识别：

| 内部字段 | 命中列名 | 用途 |
|---|---|---|
| voucher_no | 凭证编号 | 分组与回填的主键 |
| summary | 摘要 | 送模型 |
| subject | 一级科目 | 归一化后拼开关 |
| subject_name | 科目名称 | 只作辅助展示，不参与判定 |
| debit / credit | 借方金额 / 贷方金额 | 判方向、拼 `[借]/[贷]` |

两列都叫「凭证编号」（`voucher_no` 与 `voucher_num`）时取同一个，不影响结果。

### 阶段 B：建任务

```
POST /api/jobs（上传原件 + 确认后的映射）
   ↓  落盘 summary_cleaner/_storage_jobs/<id>/：原件、meta.json、status.json
   ↓  进单线程队列（GPU 不并发，避免显存争抢）
返回：job_id，状态 queued
```

前端按 1 秒轮询 `GET /api/jobs/{id}`，读 `status.json` 的 `state` 与 `progress`。

### 阶段 C：执行（五个步骤）

```
① 硬约束      四类机械凭证直接定桶 ──────────→ 136 张（1.2%），不进模型
② 归一化      剥后缀 → 别名表 → 拼 [借]/[贷] ─→ 187 维开关
③ 去重        同科目组合内压缩 ────────────────→ 11,320 → 5,100 组
④ 模型推理    第一轮 5,100 次 → 低置信组重判 ──→ 5,112 次
⑤ 写回        逐行回填 64,255 行 + 训练数据导出
```

| 步骤 | 做什么 | 量 | 耗时 |
|---|---|---|---:|
| ① 硬约束 | 员工借支 / 汇兑损益 / 资金内部往来 / 期末结转，按优先级取一个 | 命中 136 张 | 0.13s |
| ② 归一化 | 同一科目写法只归一化一次再 map 回全部行 | 616 种组合 | 0.52s |
| ③ 去重 | L1 精确 → L2 去数字 → L3 相似度 ≥0.95，同组合才比较 | 2.22:1 | 0.89s |
| ④ 推理 | 同摘要只编码一次（151 次复用）；分类头逐条跑 | 5,112 次 | 6.94s |
| ⑤ 写回 | 逐凭证落结论、组装 14 列明细 | 11,456 条 | 0.71s |
| ⑥ 训练导出（**可选**） | 只有开 `SUMMARY_CLEANER_EXPORT_TRAINING=1` 才做 | 2,526 条（全年账）/ 23,237 条（大账） | 默认 0；大账开启 +110s |

**实例（模型判定）**——送入模型的一条：

```
摘要  2509#1011待抵扣转进项税（9/26招行支付陈德华报销证券登记服务费、中登结算查询年费）
科目  应交税费[借]
      ↓ BGE 编码 + 科目开关 → 24 类 softmax
Top3  税费 1.000 | 费用 0.000 | 采购 0.000
```

科目 `应交税费[借]` 的权重直接把判断压到「税费」，摘要里的"报销/服务费"没有抢走。
这正是训练时摘要丢弃 0.3 想要的效果：**科目组合是硬信号，摘要补充语义，两者都不缺席。**

**实例（硬约束）**——下面这张凭证被规则直接定桶，不进模型：

```
2025年1月-记-1248号
  摘要  01/02 中行美元4075一般户结汇至中行基本户
  科目  银行存款(人民币户) 1459220 | 财务费用(已实现汇兑损益) -21640 | 银行存款(美元户) 1437580
  判定  汇兑损益（置信度=高，来源=程序硬约束）
```

命中逻辑：财务费用是**唯一**损益类科目 + 摘要含「结汇」+ 无往来黑名单科目。
这类凭证人工看一眼就能定，让模型去猜反而是引入不确定性（见 §3.2 关于不训练桶的说明）。

**实例（归一化与别名表）**——本账的 68 种一级科目写法**归一化后 0 处变化**，
因为它记账规范、二级科目都放在「科目名称」列。这一步在规范账上是空转，
价值在陌生账上：

| 原始写法 | 归一化后 | 靠什么 |
|---|---|---|
| 应交税金 / 应缴税费 / 应交增值税 | 应交税费 | 别名表 |
| 基本生产成本 / 辅助生产成本 | 生产成本 | 别名表 |
| 其他业务成本 | 其他业务支出 | 别名表 |
| 研发费用—折旧费 | 研发费用 | 剥后缀 |
| 中行2908（一般户） | 银行存款 | 别名表通配 `*银行*` |

陌生账上的实测差距很大：一本外部账 214 种科目令牌里 **131 种**模型没见过（57.7% 的凭证
受影响），归一化后只剩 **19 种**（17.7%），再排掉「万和」这种把客户名当一级科目的，
降到 **2.1%**。这一步不需要重训，改别名表重启即生效。

第 ④ 步的**两轮**是关键设计：

- **第一轮**只送每组的代表（5,100 次）。组内其余凭证抄结论——它们的输入在业务上等价。
- **第二轮**检查代表的最大**原始**概率：低于 0.80 且组内不止一张时，把这一组拆开各自重判
  （全年账只触发 8 组 / 17 次，大账 172 组 / 6,047 次）。

两轮合计 5,112 次调用，与逐条 11,320 次相比差异 **3 张**（0.03%）；关掉第二轮是 9 张。
机制与代价见 §4.6.2.2。

**实例（去重）**——本账最大的一组是 **259 张**外销凭证：

```
科目  主营业务收入[贷] + 应收账款[借]
摘  要  10-17外销裕富照明香港有限公司货物.D20250516/D20250520/...
        10-17外销裕富照明香港有限公司货物.D20250482/D20250555/...
        10-30外销裕富照明香港有限公司货物.D20250482/D20250555/...
        …（共 259 张，只有发票单号与日期不同）

去重   259 张 → 1 次模型调用，其余 258 张抄结论
```

单号 `D20250516` 属于数字，L2 归一化时被抹掉，259 张的归一化文本完全相同。
如果不做这一步，这 259 张会各跑一次模型，而它们的输入在业务上完全等价。

### 阶段 D：结果与导出

```
   ↓  别名重定向 → 温度校准(T=1.5) → 置信度分档 → 桶折叠（费用子桶）
   ↓  落盘：result.parquet（64,255 行原表 + 业务分类/置信度）
              detail.parquet（11,456 × 14 列）
              vouchers.parquet（复核页用，按校准概率升序）
              unknown_subjects.json
              status.json → done
可选导出：分类结果（原表回填）/ 凭证明细 / 待复核凭证 / 未知科目清单
   ↓  ≤50 万行 → xlsx（xlsxwriter）；>50 万行 → CSV（xlsx 会静默丢行）
```

结果按 job 存盘，切换模型不影响历史任务；前端"最近任务"可重新打开。

### 出错时的行为

| 情形 | 行为 |
|---|---|
| 模型交付物缺失 / 加载失败 / OOM | **直接失败**，不输出半成品（程序已无判定能力） |
| 表头识别不到凭证号或科目 | 建任务时拒绝，返回缺失字段名 |
| 行数 > 50 万 | 允许跑，导出自动切 CSV |
| 未知科目 | 不影响判定，明细标记 + 汇总成清单 |
| 某凭证无摘要 / 无科目 | 不送模型，落「未分类」并计数 |

### 全流程耗时分布

全年账 64,255 行 / 11,456 凭证，GPU（RTX 4060 Laptop 8G），冷缓存，训练导出关闭：

| 阶段 | 耗时 | 占比 |
|---|---:|---:|
| A 读表（calamine） | 1.72s | 15.7% |
| C① 硬约束判定 | 0.13s | 1.2% |
| C② 科目归一化 | 0.52s | 4.7% |
| C③ 未知科目扫描 | 0.05s | 0.5% |
| C④ 去重（L1–L3） | 0.89s | 8.1% |
| **C⑤ 模型推理（5,112 次调用）** | **6.94s** | **63.3%** |
| C⑥ 组装 + 写回 | 0.71s | 6.5% |
| **合计** | **10.96s** | |

同一本账热缓存（编码缓存全命中）只要 **4.56s**，模型段从 6.94s 掉到 0.45s。

**现在的结构是"模型 + 读表"占 79%**，其余全在 1 秒内。这跟两处改造直接相关：
硬约束向量化把 2.24s 压到 0.13s（§7.4），训练数据导出改为默认关闭，
把原来 4.11s 的「组装 + 导出 + 写盘」变成 0.71s 的纯组装。
**再优化模型以外的东西，天花板已经很低**；模型段唯一的抓手是缓存与去重（都已到位）。

> CPU 上这个分布会反过来：模型挤到 90% 以上，同规模约 53 秒（§4.6.8）。

# 二、业务桶设计

> 完整踩坑复盘见 `design/cleaner/bucket_design_principles.md`，
> 演化细节见 `design/cleaner/bucket_system_v10.md`。本章是它们的压缩与结论。

## 2.1 第一性原理

> **桶只回答一个问题：这笔钱是为哪件业务活动发生的。**
> 方向、含现、会计动作、利润影响、费用性质——全是派生维度，不进桶。

这句话否定了四种"顺手"的做法：

| 顺手做法 | 为什么不行 |
|---|---|
| 按会计科目分（管理费用桶） | 科目名不表达业务；等于硬编码，模型没有存在意义 |
| 按方向分（税费缴纳/返还） | 方向由借贷方向定，写进桶名等于二维压一维 |
| 按含现分（薪酬/计提薪酬） | 含不含现看有没有货币资金科目 |
| 按会计动作分（计提业务桶） | "计提"是记账时点，不是经济活动 |

## 2.2 解耦矩阵

| 维度 | 归属 | 载体 | 例子 |
|---|---|---|---|
| **经济活动** | **桶** | 24 桶 | 销售、薪酬、费用 |
| 方向 | 派生 | 货币资金借贷 | 税费桶 + 借=缴纳 / 贷=返还 |
| 含现 | 派生 | 有无货币资金科目 | 薪酬 + 有现=发放 / 无现=计提 |
| 会计动作 | 派生 | 无现 + 贷应付类 = 计提 | 薪酬 + 计提标记 |
| 利润影响 | 派生 | 桶属性 + 对方科目 | 清偿负债 vs 确认费用 |
| 费用性质 | 派生 | 标签（刚性/弹性/项目性） | 房租=刚性，差旅=弹性 |
| 具体类别 | 派生 | 标签（差旅/广告/FOB） | 六类之下的明细 |
| 对手方 | 派生 | 标签（客户/供应商/员工/股东） | 关联交易识别 |

**判断口诀**：能在一张凭证上读出来的（方向、含现）→ 不进桶；需要跨凭证统计才有意义的
（性质、对手方）→ 标签；决定这笔钱性质归属的 → 桶。

## 2.3 七次踩坑（浓缩）

| # | 坑 | 纠正 |
|---|---|---|
| 1 | 把"罗列"当"分类"（v4.1，53 桶） | 分类的价值在收敛，不在覆盖 |
| 2 | 把"会计科目"当"业务内容"（v7） | 同一笔电费，车间/门店/总部买的都是电 |
| 3 | 把"方向"写进桶名（v5） | 桶做归类，方向交给借贷 |
| 4 | 把"含现"写进桶（v6） | 同上，同一个病第二次犯 |
| 5 | 把"会计动作"当桶（v6 计提业务） | 计提是权责发生制的动作，不是生意 |
| 6 | 为现金流整齐而牺牲分录测试（研发并进费用） | 现金流允许多对一 |
| 7 | 部门口径残留（销售机构办公费归市场） | 办公就是办公，不管谁在用 |

## 2.4 五条铁律

1. **桶只归类经济活动**。方向、含现、会计动作、利润影响、费用性质全部解耦。
2. **按业务内容拆**，不按类别穷举、不按科目硬编码、不按部门划分。
3. **只有两种情况必须拆**：语义不明确（内部方差大）、不构成现金流单射。
4. **同一活动的正反两条线合并**（销售/退货、税费/缴纳返还、借款/取得偿还、投资/投出收回）；
   **平行活动不合并**（长期资产购建 vs 处置）。
5. **不为现金流整齐而合并**。多对一合法，牺牲分录测试的信息才是真损失。

**新桶四问**：是经济活动吗 → 是现有桶的反向吗 → 能靠"科目组合+摘要"判出来吗 →
不拆会语义混乱或不构成现金流单射吗。任何一步答"否"就停。

## 2.5 现行桶表

**33 项注册表**（32 个业务桶 + 哨兵「待复核」），其中：

| 类别 | 数量 | 处理 |
|---|---:|---|
| 硬约束（程序直接定桶） | 4 | 期末结转 / 资金内部往来 / 汇兑损益 / 员工借支 |
| 费用子桶（折叠到父级） | 5 | 办公 / 治理 / 市场 / 能源 / 中介 → 「费用」 |
| 哨兵桶 | 1 | 「待复核」，永不输出，只做兜底标记 |
| **模型训练类别** | **24** | 23 个可输出桶 + 员工借支（硬规则漏网时仍需模型兜） |

### 费用不分二级

费用曾按二级拆成 5 个子桶。拆分的初衷是给会计分录测试提供明细，但三条代价都不成立：

| 代价 | 证据 |
|---|---|
| 金标准分不准 | 5,595 条费用记录里 **1,639 条（29.3%）只标到父级**——人工自己也判不出子桶 |
| 模型学不好 | 同模型下费用族**内部互串占全部错误的 30.9%**（270/873） |
| 下游用不上 | 现金流量表只认「费用」一级，子桶不参与映射 |

折叠到父级后（同一模型、不重训）：验证集整体准确率 **93.66% → 95.62%**（+1.96pt），
费用桶自身 **62.4% → 99.2%**，真账桶数 27 → 25、费用吸收 1,198 张凭证、置信度分布不变。

折叠是**读取时**做的，`training_data.json` 里原始子桶名不动（`v2/assets/bucket_merge.json`
一行一条，删掉即回滚），`postprocess` 出口再折叠一次以兼容旧模型仍输出子桶名。

### 三条映射规则

1. **桶 + 方向查表，不需要科目裁判**。同一个桶落在两个项目上，由货币资金的借贷方向决定
   （税费缴纳 vs 返还、借款取得 vs 偿还）。
2. **多对一合法**。六个费用子桶 + 研发都映射到"支付其他与经营活动有关的现金"，
   这是设计允许的——桶的主要消费者还有分录测试，不能为了映射整齐而合并。
3. **混合到账按科目金额拆**。投资桶最典型：

| 凭证形态 | 现金流 |
|---|---|
| `交易性金融资产[贷] + 投资收益[贷] + 银行存款[借]` | 按两科目金额拆到两个项目 |
| `投资收益[贷] + 银行存款[借]`（纯分红） | 全额「取得投资收益」 |
| `交易性金融资产[贷] + 银行存款[借]`（纯赎回） | 全额「收回投资」 |

实现上通过 taxonomy 的 `cashflow_split` 字段声明触发科目与拆分科目。
混合到账若无法可靠拆分，落「待复核」并给出金额建议，**不做猜测性拆分**。

# 三、程序侧

程序只做**确定性**工作：读表、科目归一化、四类机械凭证定桶、写回与导出。
业务桶的判定 100% 由模型完成，程序不参与任何"打分"或"投票"。

## 3.1 职责边界

| 程序做 | 程序不做 |
|---|---|
| 读表与字段映射（含自动识别） | 给业务桶打分 |
| 科目归一化（剥后缀 + 别名表 + 拼方向） | 关键词 / 金额 / 制单人偏置 |
| 四类机械凭证直接定桶 | 与模型结果融合 |
| 未知科目扫描与清单输出 | 从人工纠错里学习权重 |
| 写回、导出、训练数据导出 | 决定"模型犹豫时听谁的" |

顺序固定，不可交换：

```
读表 → 归一化（含未知科目扫描）→ 模型识别 → 硬约束覆盖 → 写回 / 导出
                    ↑                              ↑
              未知科目在这里就能知道          只覆盖硬规则命中的凭证
```

## 3.2 四类机械凭证的直接定桶

这四类凭证的业务性质由科目形态唯一确定，不需要语义判断，因此不走模型：

| 规则 | 判据 | 桶 | 优先级 |
|---|---|---|---:|
| 员工借支 | 其他应收款 + 员工姓名 / 借支还款措辞 | 员工借支 | 4 |
| 汇兑损益 | 期末调汇（外币科目 + 财务费用-汇兑损益） | 汇兑损益 | 3 |
| 资金内部往来 | 一级科目**全部**为货币资金（银行存款/库存现金/其他货币资金互转） | 资金内部往来 | 2 |
| 期末结转 | 凭证号为结转损益凭证 | 期末结转 | 1 |

优先级数字越小越优先（同一张凭证命中多条时取小的）。硬约束命中率在真实账上约 1.2%
（136 / 11,456：结转 10、资金内部 76、汇兑 42、借支 8），这部分凭证的置信度直接记「高」，
不产生模型调用。

> **不训练桶的代价**：汇兑损益 / 资金内部往来 / 期末结转的样本被剔除出训练集
> （它们由硬规则定桶，进训练是死重）。副作用是**模型对这三类业务没有任何概念**——
> 一旦硬约束漏网（如摘要写"调整外币账户余额"而没有"汇兑/结汇/收汇"字样），
> 模型会把它当普通业务瞎判。实测把结汇凭证直接喂给模型，输出是"采购"或"结算手续费"，
> 与真实业务无关。
>
> 这是当前设计的已知盲区：硬约束的召回率决定了这三类凭证的可靠性，
> 而不是模型的准确率。补模型没意义（没有训练样本），只能收紧规则或补别名。

## 3.3 未知科目扫描

归一化之后、推理之前就能判定哪些科目模型没见过，判据是交付物 `subject_to_index.json`
（一个 5KB 的开关表），**不需要加载模型**。上传预览阶段即可返回清单。

未知科目按处理方式分三类——混为一谈会把"标准科目但模型没学过"误判成"别名表没维护"，
白折腾：

| reason | 含义 | 处理 |
|---|---|---|
| `alias_candidate` | 不在标准一级科目表（168 个）里 | 别名表大概率能映射（应交税金 → 应交税费） |
| `need_training` | 是标准科目，但模型没学过 | 别名表无效，只能补样本重训 |
| `direction` | 名字认识，但这个借贷方向没出现过 | 罕见，补样本 |

反向问题单独统计：`model_only_subjects`——**模型认识、但不是标准科目**的名字
（往来单位名、二级科目混进一级科目列，如 `万和`、`Sunland Co.,Ltd.`）。
它们不会被判成未知，但会稀释科目开关的表达力，属于训练数据卫生问题。

清单里每条带 `raw_names`（原始写法）与 `sample_summaries`：维护别名表要的是
"原始写法 → 标准科目"，只给归一化后的名字看不出该写哪条规则。

未知科目的凭证**照常交给模型**（模型仍能按摘要判断），不降置信度、不特殊处理，
只在明细里标出、在统计里汇总，作为"该维护别名表了"的信号。

> 实测：这本全年账 7 个未知科目 / 10 张凭证（0.1%），全部是 `direction`（结账方向，
> 如 营业外收入[借]）；`model_only` 40 个。扫描耗时 2.7s / 6.4 万行。

## 3.4 业务桶为什么不用规则兜底

程序侧曾经有一套完整打分：PMI 相关性传播、手工关键词、自动词学习、金额分布惩罚、
人工纠错顺位、制单人偏好。逐项关掉的实测（真实账 8,000 行 / 1,453 凭证）：

| 关闭的机制 | 程序原生桶变化 | **最终输出桶变化** |
|---|---:|---:|
| 结构分（PMI 传播） | — | 0 |
| 自动词学习 | — | 0 |
| 纠错 / 制单人 | — | 0（两者非空率本就是 0%） |
| 手工关键词 + 金额特征 | 有（关键词偏置最高到 2.0） | **0** |
| **全部关掉（只剩锚定）** | **20.6%** | **0.0%** |

扩充到全年账 11,456 张凭证复测：程序分数全开 vs 全关，最终桶 **0 条差异**；
与"纯模型"相比只差 **3 张（0.03%，都在费用父级与子桶之间，现已随子桶合并消失）**。

原因在数学上很直接：程序只是同一份摘要的另一种读法，而模型在同一份摘要上学过语义，
且 top1 概率通常 >0.95。规则要翻盘，必须让模型的判断本身处于犹豫区——
那正是低置信、本来就该进复核清单的样本。**规则在模型不确定时也没有更好的信息可用，
它知道的并不比模型多。**

# 四、模型侧（V3.0）

## 4.1 架构

```
摘要整句 ──→ BGE-large 编码器（24 层 / 1024 维）──→ [CLS] 1024 维
科目组合（187 维 0/1 multi-hot）──→ Linear(187→64) ──→ 64 维
              concat 1088 ──→ Linear(1088→256) → ReLU → Dropout(0.1) → Linear(256→24)
              ──→ logits ──→ softmax ──→ 温度校准
```

两条输入走完全不同的路径：**编码器只读摘要，科目不进编码器**。科目是单层线性
`Linear(187→64)`，输入为 0/1，等价于"把命中的科目行权重相加"——实测 3,000 条耗时 0.4ms，
占推理总时间的 0.0%。摘要则必须走完 24 层注意力，占 99% 以上的计算。

| 项 | 值 |
|---|---|
| 编码器 | `BAAI/bge-large-zh-v1.5`（24 层 / 1024 维 / 326M 参数） |
| 微调策略 | 全量微调（编码器 + 分类头） |
| batch / maxlen | 4 / 64 token（训练）；推理按设备分批（见 §4.6） |
| 交付 4 件套 | `fine_tuned/`、`finance_classifier.pt`、`index_to_bucket.json`、`subject_to_index.json` |

训练时科目开关维度是 187、输出 24 类；两者都随训练数据重新生成，不是常数。

> 当前 `.pt` 仍是 **29 类**（训练时费用子桶还在），费用子桶在 `postprocess` 出口折叠到父级，
> 对外呈现 24 类。删除 `bucket_merge.json` 里的条目即回到 29 类口径。
`schema` 校验会逐项比对 `subject_to_index.json` 与 `.pt` 内嵌索引，不一致直接报错，
避免"同数量不同名"的静默错位。

## 4.2 为什么是分类，不是向量检索

早期（v2）用 Triplet Loss 学 embedding + 最近邻聚类；v3 起改为监督分类。区别：

| | 向量检索 | 分类（现行） |
|---|---|---|
| 判断方式 | 算相似度找最近样本 | 29 路 softmax 直接学边界 |
| 谁决定标签 | 邻居投票 | 模型自己输出 |
| 能否表达口径 | 不能（"费用父级宽松"没法编码） | 能（从样本里学） |
| 新增桶 | 加样本即可，无需重训 | 必须重训 |

代价是"加桶要重训"，收益是边界更清晰、置信度可用。对 29 个语义高度重叠的桶，后者更合适。

## 4.3 科目归一化（模型之前的前置步骤）

顺序固定：**读原始一级科目 → 剥后缀 → 查别名表 → 拼科目组合 → 送模型**。

| 步骤 | 函数 | 做什么 |
|---|---|---|
| 剥后缀 | `split_suffix` | 按 `— - – / · （）` 等分隔符机械切主干，只留一级科目 |
| 查别名 | `alias_of` | 映射表 `{"match": [...], "to": "标准科目"}`，`*` 作通配 |
| 组合 | — | `f"{标准科目}[借/贷]"` multi-hot |

**为什么必须在拼组合之前做**：模型的输入是"科目开关"，不是文本。`研发费用—材料费`
和 `研发费用` 在词表里是两个维度，前者没学过就等于没信号。

实测效果（一本陌生账，2,104 条去重记录）：

| 指标 | 改前 | 改后 |
|---|---:|---:|
| 未知科目种类 | 131 | **19** |
| 未知次数 | 1,631 | **400** |
| 含未知科目的凭证 | 57.7% | **17.7%** |
| 排除「万和」这类客户名当科目后 | — | **2.1%** |

安全阀：归一化后的名字不在词表、而原名在 → 保留原名（绝不把认识的开关改坏）。
方向缺口兜底：词表里同名科目只有另一方向时，用那一方向的开关。

维护：`_dev/scripts/list_unknown_subjects.py` 按频次列出未知科目，贴进映射表即可，
**不用重训**。骨架由 `_dev/scripts/build_subject_alias_table.py` 生成（102 条标准科目）。

## 4.4 训练数据管线

```
分类结果 → 按凭证号分组 → 记录级去重（精确 + 相似）→ count 计数 → 金标准 training_data.json
```

要点：

| 项 | 做法 | 原因 |
|---|---|---|
| 去重粒度 | `(归一化摘要, 排序后的科目组合)` | 同摘要同科目 = 同一样本，count 累加 |
| count 展开上限 | `MAX_COUNT_EXPAND = 20` | 防单条高频样本膨胀失控 |
| 划分 | 先按**记录**分层 80/20，再各自展开 | 先展开再切会让同一条记录的展开样本同时进训练和验证 → val_acc 虚高 |
| 头部缩放 | 单桶有效样本上限 12,000，**只作用于训练侧** | 头部占 57.8%，缩放后 46.4%；**不删记录**，按 12,000/现有 等比缩放 |
| 验证集 | 保持真实分布，不缩放 | 配平后测不出真实表现 |
| 跳过桶 | 未分类 / 无法分类 / 期末结转 / 资金内部往来 / 汇兑损益 | 机械凭证或硬规则 |

实测（v10.2）：训练 40,680 / 验证 12,649，头部占比训练侧 46.7%、验证侧 55.9%。

## 4.5 训练方法

### 摘要丢弃（`--summary-dropout 0.3`）

训练时按概率把摘要置空（只留 `[CLS]/[SEP]`），逼模型学"科目组合 → 桶"而不是背摘要字面。

动机见 §6.4：模型一度对 `发出商品[借]+库存商品[贷]`（金标准里 3,874 count 100% 成本结转）
这个组合判成采购，因为它只记住了"发出商品--XXX客户"这个句式。

### 其他参数

| 参数 | 值 | 依据 |
|---|---|---|
| encoder | bge-large-zh-v1.5 | 与 v10 保持一致才可比 |

| 损失 | CrossEntropy | |

## 4.6 推理链路与耗时

### 4.6.1 一条凭证在模型里走的每一步

| 步骤 | 输入 → 输出 | 说明 |
|---|---|---|
| ① 分词 | 摘要字符串 → `input_ids`（≤64 token） | 中文按字/词切，批内动态 pad |
| ② 科目查表 | `一级科目[方向]` → 187 维 0/1 | 归一化后查开关下标，查不到置 0 并记未知 |
| ③ 编码 | `[B, L]` → `[B, L, 1024]` | 24 层自注意力 + 前馈，逐层混合上下文 |
| ④ 池化 | → `[B, 1024]` | 取第 0 个位置（`[CLS]`）的末层隐状态 |
| ⑤ 科目压缩 | `[B, 187]` → `[B, 64]` | 0/1 输入下等价于命中行求和 |
| ⑥ 拼接判桶 | `[B, 1088]` → `[B, 29]` | Linear → ReLU → Linear |
| ⑦ softmax | → 29 类概率 | 温度校准在后处理做（§5.2）；费用子桶再折叠为 24 类 |

模型不是"摘要里出现某词 → 判某桶"的匹配器。摘要在 ③ 被压成一个 1024 维语义点，
科目组合在 ⑤ 被压成 64 维，⑥ 学的是**"这类语义点 + 这组科目"落在哪个桶的区域**。
所以它能处理训练集里没出现过的措辞——代价是必须跑完 24 层。

### 4.6.1.1 走查：一条「9月工资发放」的凭证

维度与下标取自当前交付物（187 个科目开关 / 1024 维 / 64 维 / 256 维）。

**输入**

```
摘要  9月工资发放
科目  应付职工薪酬[借]、银行存款[贷]
```

**① 分词**——中文按单字切，数字与英文按 WordPiece

```
[CLS] 9  月  工  资  发  放  [SEP]
 101 130 3299 2339 6598 1355 3123 102
```

批量时按**批内最长**补齐（`padding=True`），不是固定补到 64。

**② 科目查表**——187 维 0/1 多热

```
应付职工薪酬[借]  → 第 95 位
银行存款[贷]      → 第 167 位
其余 185 位        → 0
```

查不到的科目保持 0，同时记进 `unknown_subjects`（§3.3）。

**③ 编码**——24 层，每层 1024 维

```
[B, 8] → [B, 8, 1024]
```

每层两件事：self-attention 让这 8 个 token 互相看，FFN 各自变一次形。逐层把上下文混进去，
到最后一层，`[CLS]` 这个位置已经"读完整句"。

**④ 池化**——取第 0 个位置的末层隐状态

```
[B, 8, 1024] → [B, 1024]
```

**⑤ 科目压缩**——单层线性，0/1 输入等价于查表求和

```
Linear(187 → 64)
输入只有两个 1，所以这一步 = weight[95] + weight[167] + bias → [B, 64]
```

这一步实测 0.4ms / 3,000 条，占推理总耗时 0.0%。

**⑥ 拼接判桶**

```
concat([1024, 64]) = 1088
→ Linear(1088 → 256) → ReLU → Linear(256 → 29)
```

中间这层 256 维隐层学的是**"这类语义 + 这组科目 → 哪个桶"的组合规则**。单靠摘要或单靠科目都不够：
「发放」这个词在采购、销售、薪酬里都出现，只有配上 `应付职工薪酬[借]` 才唯一指向薪酬。

**⑦ softmax → 概率 → 分档**

```
29 个 logits → softmax → 薪酬（下标 18）概率最高
→ 温度校准 T=1.5 → 校准概率 → 高/中/低 → 费用子桶折叠到父级
```

### 4.6.1.2 为什么它能认没见过的说法

摘要在 ③ 被压成 1024 维空间里的**一个点**，同一类业务（工资、奖金、社保、离职补偿）
在空间里聚成一簇；科目向量在 ⑤ 把这个点往对应区域推一点；⑥ 在簇之间画边界。

所以「发放9月薪资」这种训练集里没出现过的说法也能落到薪酬簇——它在语义空间里本来就靠近
「9月工资发放」。这正是 A 组（陌生措辞）从 41.7% 提升到 95.0% 的原因：
摘要丢弃训练逼模型别只看字面，而是学科目组合与语义的对应关系。

代价也很直接：**必须跑完 24 层注意力**，这是它比"关键词表 + 规则"慢两个数量级的原因。
关键词匹配是 O(词表)，语义编码是 O(24 × 序列长度² × 1024²)。

### 4.6.2 业务等价的凭证只判一次

同一笔业务在序时账里按月重复，摘要只差期间与金额：

```
支付1月当期税费1000元   应交税费[借] + 银行存款[贷]
支付2月当期税费2000元   应交税费[借] + 银行存款[贷]
```

科目组合一笔不差、摘要只差数字，业务性质显然相同。逐张送模型等于把同一道题做 N 遍。
送模型之前先做三层压缩（成本递增、收益递减）：

| 层 | 判据 | 压缩比 | 风险 |
|---|---|---:|---|
| L1 精确 | 摘要 + 科目组合完全相同 | 1.03:1 | 零（输入相同，输出必相同） |
| L2 数字归一 | 去数字/单号/标点后相同 | **2.01:1** | 零（差异只是数字） |
| L3 相似度 | 同组合内归一化后相似度 ≥ 0.95 | 累计 **2.22:1** | 低（文本有细微差异） |

**同科目组合是硬前提，不是优化而是正确性约束**：

```
「支付当期税费」应交税费[借] + 银行存款[贷]
「支付当期水费」应付账款[借] + 银行存款[贷]
```

两句话去掉数字后相似度约 0.8，但即便更高也不能合并——业务性质完全不同（税费 vs 费用）。
科目组合不同就绝不比较，这一条挡住 L3 的主要误合并来源。

**L1 在真实账上几乎不命中**（1.03:1）：摘要普遍带日期、银行账户号、单号，
"业务相同"几乎从不等于"文本相同"。收益全在 L2。

**送模型的代表用组内第一条原始摘要**（保留数字），模型看到的是真实文本；
归一化只用于判重，不改输入。

实测（全年账 11,456 凭证 / GPU）：

| 项 | 逐条 | 去重后 |
|---|---:|---:|
| 模型调用 | 11,320 | **5,100**（2.22:1） |
| 模型推理 | 12.08s | **7.17s** |
| 去重本身 | — | 0.76s |
| 端到端 `pipeline.run` | 20.5s | **15.1s**（−26%） |

**代价是 9 张凭证（0.08%）判桶改变**，来源有两类：

1. **模型本身前后不一致**：同一业务在不同月份被判到不同桶（如"建行账户管理费"6 月判
   费用、7 月判结算手续费）。合并后强制一致——这类"差异"本来就是噪声，去重反而修好了。
2. **模型在同类凭证上给出两个答案**：`预付欧时达设备款 办公桌 43 张`（12,126 元）被判
   费用，`办公桌 460 张`（49,680 元）被判长期资产购建。两张凭证的科目**完全相同**
   （应付账款 + 银行存款，科目名称都写着"固定资产类"），业务性质没有差别——
   模型判岔了。合并后两者统一（这次统一到了错的那个），**错误的组代表会被放大到整组**。

第 2 类揭示的是模型在边界样本上的不稳定，不是去重的缺陷——但**代价确实被去重放大**：
同一组里代表判错，全组跟着错。这类样本值得单独进复核清单：组内原本判定不一致，
本身就是"模型在这类业务上不可靠"的信号。

L3 可以用 `SUMMARY_CLEANER_DEDUP_SIM=1.05` 关掉（回到只做 L1+L2），但 L2 本身没有开关——
它是这套优化的主体，代价 4 张（0.03%）。

这 9 张里有一半来自"代表自己也不确定"的组。开启低置信组重判后（§4.6.2.2），
差异从 9 张降到 **3 张**，代价只是少数组的额外调用。

### 4.6.2.1 压缩比是每本账的属性

2.22:1（压掉 55%）是这本账的水平：摘要是「日期 + 银行账户号 + 供应商 + 业务描述 + 金额」
的混合体，即使去掉数字，供应商名与业务描述仍各不相同。

作为上限参考：把摘要按"前 4 个字即业务类型"折叠（模拟"计提工资""支付房租"这种规整写法），
压缩比能到 **5.87:1（压掉 83%）**。真实账落在这之间，取决于记账习惯。

所以不要假设任何固定压缩比——`stats.dedup.ratio` 会在每次跑账时输出真实值，
前端可直接展示"模型判定 5,100 次 / 涉及 11,320 张凭证"。

### 4.6.2.2 组代表不确定时，把组拆开重判

去重的收益是"判一次、抄 N 张"，代价是**代表的错误被放大 N 倍**。当代表本身就没把握时，
这个交换不划算：模型在这类业务上犹豫，组内本来就可能有分歧，整组抄一遍等于把一次犹豫
复制成 N 张。

触发条件（两个都满足才重判）：

1. 组内 **≥2 张**（单张没得拆）
2. 代表的最大原始概率 **< 0.80**（与"高置信"同一条线；`SUMMARY_CLEANER_DEDUP_RECHECK`，设 0 关闭）

动作：把该组每个成员按**自己的原始摘要 + 自己的科目组合**重新拼成输入，批量前向一次；
成员用各自的结论**覆盖**代表，不再抄作业。判定链路其余部分不变（别名合并、后处理、校准、分档）。

大账实测（84.7 万行）：

| 项 | 值 |
|---|---:|
| 触发组数 | **172** / 40,318（0.4%） |
| 重判条数 | **6,047**（平均 35 张/组，是"同一模板换编号"的大组） |
| 额外调用 | +6,047（占 46,365 的 15%，按 870 次/秒约 **+7s**） |
| **结论改变** | **8 张**（5 组），占重判量的 0.13% |
| 代表桶分布 | 采购 5,276 / 成本结转 249 / 生产制造 182 / 费用 157 / 销售 49 |

8 张的改动方向：`费用 ↔ 研发`（差旅费属技术支持部还是研发）、`税费 → 采购` 3 张
（`收到发票，计提进项税（招行支付进口报关单…）`）、`结算手续费 → 采购` 1 张。
都是"同一组里两个业务边界"的典型，不是随机抖动。

**结论：重判几乎不改变结果（0.13%），它的价值不在改判，而在把"组代表犹豫"这件事
从 1 张扩散成 35 张之前拦住**——重判后的每张拿到的是自己的概率，置信度不再被代表绑架。
成员各自落到的桶：采购 5,280 / 成本结转 249 / 生产制造 182 / 费用 157 / 销售 49。
采购桶合计 6,047 张中置信（占全部中置信 78%），复核清单的主体仍在这里。

代价可以精确控制：关掉（`SUMMARY_CLEANER_DEDUP_RECHECK=0`）省 15% 调用与约 7 秒，
代价是 8 张跟着代表走、以及这 6,047 张的置信度退回代表的水平。

### 4.6.3 摘要编码复用：同一句话只读一遍

encoder 的输入只有摘要，科目走独立的 `Linear(187→64)`，**科目不进编码器**。
所以同一句摘要无论配什么科目组合，输出的 1024 维向量逐位相同——
**同一轮内，同摘要的多条只需编码一次；分类头仍要逐条跑**（结论依赖科目）。

**实例**（这本账里真实存在的同摘要多科目，共 121 组）：

| 凭证 | 科目组合 | 判定 |
|---|---|---|
| 2025年1月-记-0143 | 主营业务成本[借] + 其他应付款[贷] | 采购 |
| 2025年3月-记-1110 | 其他业务支出[借] + 其他应付款[贷] | 费用 |

摘要都是「#/#香港代付C&C全球物流有限公司海运费用」。两句的编码一模一样，
但结论不同——所以省的是编码，不是分类。

#### 复用的边界在 dedup 之后

| 层 | 复用条件 | 作用 | 压缩比 |
|---|---|---|---:|
| dedup（§4.6.2） | 同科目组合 + 摘要相似 | 复用**结论** | **2.22:1** |
| **编码复用** | 归一化摘要相同（科目可不同） | 复用**编码** | 见下 |

dedup 已经把"摘要相同且科目相同"的合并掉了，编码复用只剩"**摘要相同、科目不同**"
这一块。真实账里这块很小：

| 账 | 送模型条目 | 唯一归一化摘要 | 同轮复用 | 同摘要多科目组 |
|---|---:|---:|---:|---:|
| 全年账 | 5,100 | 4,949 | **151（3.0%）** | 121 组 / 272 条 |
| `case/序时账1.xlsx` | 1,558 | 1,525 | **33（2.1%）** | 28 组 / 61 条 |

原因很直接：一笔业务通常就是一个科目组合，同一句话配两三种科目的情况占 2%–3%。

#### 缓存键是归一化摘要

`summary_key(_normalize_summary(摘要))`——抹掉数字、单号、标点后做键，
所以「支付1月税费1000元」与「支付2月税费2000元」同键，共享一条向量。
用原始摘要做键则几乎不命中（摘要都带日期、账号、供应商）。

#### 落盘缓存是副产品，不是主收益

实现上向量会写进 `_storage/embed_cache.db`（SQLite，按归一化摘要存 fp32 1024 维，
一条 4KB）。这让**同一份账再跑一次**时编码归零：

| 场景 | pipeline | 命中率 |
|---|---:|---:|
| 全年账 · 首次 | 9.24s | 0% |
| 全年账 · 同账再跑 | **2.78s** | 100% |
| `case` · 首次 | 2.65s | 0% |
| `case` · 同账再跑 | **0.73s** | 100% |

但**这一层用结果缓存（摘要+科目 → 桶与置信度）也能拿到，而且更彻底**（连分类头一起省）。
编码复用的独立价值只在同轮那 2–3%，跨轮部分是顺带。

#### 四条实现约束

1. **必须带模型指纹**。CLS 向量是权重的产物，换模型后旧向量全错。
   表里存 `finance_classifier.pt` 的 md5 前 12 位，不匹配视为未命中。
2. **冷跑也要按归一化摘要归并**。如果冷跑各算各的、热跑才共享，同一份账跑两次
   结果会不一样——审计不可接受。归并发生在编码阶段，与缓存是否命中无关。
3. **fp32 存，不省那点空间**。fp16 存过一轮：2,216 条里 1 条 top1 翻转、概率差 0.16，
   边界样本上半个精度位就能翻盘。22MB 换"结果可复现"是划算的。
4. **输入仍是原文，不是归一化摘要**。看起来"把摘要统一去数字再送模型"更干净
   （同键的条目输入完全相同，连共享逻辑都不需要），但训练数据的摘要
   **72% 带数字**（24,790 条里 17,946 条），全量归一化等于把推理输入挪到
   训练分布之外。实测那样做会让 **52 张凭证（0.46%）判桶改变**，
   而"共享首条原文向量"只改 2 张（0.02%）。归一化只用于**判重**，不改输入。

### 4.6.4 时间构成

**GPU（RTX 4060 Laptop 8G，11,456 凭证 / 全年账）**

| 阶段 | 修复前 | 修复后 | 占比 |
|---|---:|---:|---:|
| 建科目开关（含归一化） | 0.65s | 0.65s | 5.5% |
| tokenize | 0.24s | 0.24s | 2.0% |
| **GPU 前向** | 11.0s | 11.0s | **94%** |
| **概率转 dict** | **5.73s** | **0.09s** | — |
| 合计 | 17.64s | **11.71s** | 979 条/秒 |

「概率转 dict」原本占 32.5%，原因不在数据量：`float(p[j])` 每读一个 CUDA 标量都要一次
`cudaMemcpy` 加隐式同步，1.1 万条 × 24 桶 = **33 万次同步**，显卡一直在等 CPU 伸手取数。
改为每批一次 `.cpu().numpy()` 后，概率逐位相同（最大差 0.00e+00），明细 md5 不变。
端到端 31.6s → **25.3s**。

**CPU（16 线程，2,216 凭证 / `case/序时账1.xlsx`）**

| chunk | 吞吐 | 与 GPU 全精度结果的 top1 差异 |
|---:|---:|---:|
| **32（默认）** | **96 条/秒** | **5 / 2,216（0.23%）** |
| 64 | 79 条/秒 | 6 / 2,216（0.27%） |
| 128 | 59 条/秒 | 9 / 2,216（0.41%） |
| 256 | 54 条/秒 | 6 / 2,216（0.27%） |

**两端的最优 batch 方向相反**：GPU 靠大 batch 喂满流处理器（128/256 最优，1024 掉到 540 条/秒），
CPU 靠小 batch 保住缓存命中（32 最优，128 掉到 59 条/秒）。所以 `chunk_size` 按设备自动取，
不写死。CPU 的 int8 动态量化按批内激活定 scale，批越大越偏离全精度——chunk=32 恰好
既最快又最准。

### 4.6.5 为什么准备不了 KV cache

KV cache 解决的是**自回归解码的重复计算**：生成第 t 个 token 时，前 t−1 个 token 的
Key/Value 已经在之前算过，缓存下来就不必重算前缀，把 O(n²) 的累积代价摊平成 O(n)。

本模型是 **encoder-only + 定长分类**，两个前提都不成立：

| 前提 | 自回归生成 | 本模型 |
|---|---|---|
| 是否逐 token 产生输出 | 是，一次一个 | 否，一次前向出全部 24 个桶 |
| 同一 token 的 K/V 是否被重复计算 | 是，每步重算整段前缀 | **否，每个 token 只算一次** |
| 序列是否分多步推进 | 是 | 否，`[CLS]...摘要...[SEP]` 一次算完 |

也就是说，第 ③ 步里每一层确实算 Q、K、V 三个投影，但**每个 token 只算一遍**，不存在
"前缀被反复计算"的对象，缓存无处可存。硬要复用只有一种场景：不同请求共享完全相同的
前缀 token（如统一的 prompt 模板）。实测这本账摘要的前缀分布：

| 前缀长度 | 不同前缀数 | 最高频前缀占比 | Top3 合计 |
|---:|---:|---:|---:|
| 4 token | 875 种 | 9.6% | 19.9% |
| 8 token | 1,603 种 | 3.6% | 6.8% |

摘要中位仅 31 字（约 20 token），前缀高度分散、没有统一模板，前缀复用的命中率支撑不起
额外复杂度。

> 前缀复用行不通，不代表缓存行不通。**换粒度就行**：缓存"整句算完的 CLS 向量"
> 而是"整句摘要的编码结果"——同一句摘要配不同科目只编码一次（§4.6.3）。
> 注意这条路的收益只有 2%–3%，因为真实账里"一句话配多种科目"的情况很少。
>
> 附带说明为什么"缓存最终结果"很弱：摘要完全相同（连数字都一样）的只占 **2.8%**，
> 而缓存读题结果的命中率是 45–60%。差一个数量级。

### 4.6.6 已到位的优化

| 项 | 现状 | 依据 |
|---|---|---|
| 精度 | 已是 fp16 | 手测 fp32 慢 **9.8×**（56 vs 547 条/秒）：Ada 卡的张量核只吃 fp16/bf16 |
| padding | 利用率 **99%** | 按长度排序后分批，批内长度几乎相同，只浪费 1% |
| 注意力实现 | SDPA | `use_cache=False`、无 gradient checkpointing |
| 分类头 | 0.4ms / 3,000 条 | 187→64→1088→256→24 是小矩阵，不值得优化 |

> 曾经把 3,000 条一次性 pad 到 64 算出"56% 的计算是 padding"——那是**假象**。
> 真实路径每批独立 pad，且批内已按长度排序。

### 4.6.7 GPU 利用率只有约 30%

按 979 条/秒、平均 28.9 token 反推，实际算力约 17 TFLOPS，而该卡 fp16 峰值约 60 TFLOPS。
差距来自小 batch 的 kernel launch 开销与显存带宽——**不是算法问题，改 Python 拿不到**。
剩余的提速手段只有两类，且都要付代价：

| 手段 | 收益 | 代价 |
|---|---|---|
| ONNX Runtime / TensorRT（固定 shape 图） | 1.3–2.5× | 要转图、要按长度分档固定 shape、精度需重新回归 |
| 换小编码器（bge-base 768 维 / 12 层） | 约 3× | 必须重训；实测 B 组组合推理会退步（成本结转 17/30 → 28/30 是反向） |

### 4.6.8 面向实际部署：CPU 才是常态

产品面向财务用户，绝大多数机器没有独立显卡，也不应要求用户安装 CUDA 运行时。
CPU 路径使用 **int8 动态量化**（`torch.quantization.quantize_dynamic`，仅量化 Linear 层），
模型体积 1.3GB → 350MB，吞吐从 fp16-on-CPU 的 2.5 条/秒提到 **96 条/秒**（约 38×，
`case/序时账1.xlsx` 实测）。量化前后在 300 条金标准上判桶一致率 97.33%。

**去重在 CPU 上比在 GPU 上值钱得多**：模型是 CPU 的绝对瓶颈，把调用次数砍到 45%
就等于把等待时间砍掉一半以上。按去重后 2.22:1 折算（96 条/秒、约 5.7 行/凭证）：

| 账的规模 | 凭证数 | 模型调用 | 逐条 | **去重后** |
|---|---:|---:|---:|---:|
| 1.2 万行（`case/序时账1.xlsx`） | 2,216 | ~1,560 | 23s | **16s** |
| 6.4 万行（全年账） | 11,456 | 5,100 | 2.0 分钟 | **53s** |
| 57 万行 | 10 万 | 4.5 万 | 17 分钟 | **8 分钟** |
| 200 万行 | 35 万 | 15.8 万 | 61 分钟 | **27 分钟** |

同规模 GPU 是 11.7 秒 / 6 分钟，相差约 10 倍。**所以 CPU 的量化与运行时选择，
比 GPU 上的任何微调都更决定用户体验**；而调用次数（去重）是唯一能在不改模型的前提下
直接砍半的手段。

> 压缩比随账而变：这本账摘要带大量银行账户号与供应商名，去数字后仍有差异。
> 若某本账的摘要是"计提X月工资"式的规整写法，L2 的压缩比会明显高于 2.2:1。

# 五、置信度

## 5.1 温度校准

模型概率高度饱和：验证集 top1 均值 0.992、>0.99 占 95.4%。因此必须做温度缩放
（`softmax(log(p)/T)` 与 `softmax(z/T)` 等价，无需模型暴露 logits）：

$$P_{cal}(b) = \frac{\exp(\log p_b / T)}{\sum_{b'}\exp(\log p_{b'} / T)},\qquad T = 1.5$$

温度是按 **ECE（期望校准误差）** 选的，不是 NLL：

| T | 高置信覆盖 | 高置信档错误率 | 低置信占比 | ECE |
|---:|---:|---:|---:|---:|
| 1.0 | 94.0% | 6.4% | 0.9% | 0.023 |
| **1.5** | 89.2% | 5.4% | 2.2% | **0.011** |
| 2.0 | 84.0% | 4.1% | 6.0% | 0.023 |
| 4.0 | 46.1% | 2.5% | 21.6% | 0.196 |

按 NLL 最小化会选到 T=4：NLL 被"自信地判错"的少数样本绑架（4% 的错判贡献 93% 的 loss），
压平它们降 NLL 最快，代价是把 94% 判对的也一起压平——高置信档只剩 46% 覆盖，
21.6% 的正常凭证被打成低置信。**T=1.5 才是校准误差最小的点。**

## 5.2 置信度分档

| 档 | 条件 | 用途 |
|---|---|---|
| 高 | $P_{cal} \ge 0.80$ | 可直接采信 |
| 中 | $0.50 \le P_{cal} < 0.80$ | 建议抽查 |
| 低 | $P_{cal} < 0.50$ | 必须人工复核 |

硬约束凭证直接记「高」，不参与校准。

## 5.3 分档的实际质量

验证集 4,666 条**记录**（v10.4 / bge-large 5 轮，24 桶，剔除对抗样本后）：

| 档 | 记录数 | 占比 | 判错 | 档内错误率 |
|---|---:|---:|---:|---:|
| 高（≥0.80） | 4,355 | 93.3% | 128 | **2.94%** |
| 中（0.50–0.80） | 255 | 5.5% | 85 | 33.33% |
| 低（<0.50） | 56 | 1.2% | 26 | 46.43% |
| 整体 | 4,666 | — | 239 | 5.12% |

含义：高置信档 93.3% 的覆盖面里只错 2.94%，可以按"抽检"对待；中 + 低共 311 条（6.7%），
命中率高，人工复核的投入产出合理。

> **口径说明**：本表是**记录级**（一条记录算一次），v10.3 那张表是**展开样本级**
> （`split_records` 按 count 复制后算），两者不可直接比。改用记录级是为了避免
> 高频样本（count 最高 40）主导指标——曾因在展开样本上又乘一次 count 得到
> "5,419 条错误"，实际只有 582（平方放大 9 倍）。
>
> 从 v10.3 到 v10.4，高档错误率 4.33% → **2.94%**、整体 6.34% → **5.12%**，
> 即使口径有差异，下降幅度也远超口径带来的噪声。

> **风险提示**：降低温度会把"系统性错误"从低置信推到高置信。曾出现某类凭证
> （`交货` 措辞）673 count 判错、降 T 后有 636 count 变成高置信。
> 结论是**高置信档的质量取决于最大的那一个系统性错误，而不取决于 T**——
> 解决方式是补样本或改训练方法，不是把 T 调回去（T=4 等于用 21.6% 的低置信掩盖 6.4% 的错误）。

## 5.4 父子回退已不存在

注册表里唯一的一组父子关系是「费用 → 5 个费用子桶」，随 §2.5 的子桶合并一并消失。
因此「低置信回退到父级」这条规则在当前桶表下没有可触发的对象：低置信凭证保持原判、
进入复核清单，不再被改判到父桶。

### 对抗样本：按错误位置补，成对生成

两侧只改一处（摘要或科目），共 1,560 条。

覆盖的错误结构（按验证集训练权重）：`费用→采购 27.3%`、`薪酬→采购 9.1%`、
`长期资产购建→采购 7.0%`、`采购→费用 6.0%`、`税费→采购 4.3%`。

| 目标桶 | 组数 | 对照 | 目标桶 | 组数 | 对照 |
|---|---:|---|---|---:|---|
| 费用 | 200 | 采购 65 / 长资 85 / 生产 22 | 采购 | 80 | 费用 200 / 税费 60 |
| 长期资产购建 | 120 | 费用 20 | 生产制造 | 70 | 折旧 25 |

**两条必须记住的经验**：

1. **通过率不能当泛化证据**。训练前 89.7%，训练后 99.0%——但这 780 组已经进了训练集，
   99% 只说明"模型学会了这些样本"。真正的泛化证据是 A/B/C 的提升
   （尤其 A 组是训练集外的陌生措辞）和真账那 97 张差异。
2. **`count=1` 的权重远低于现有样本**。现有高频样本 count 到 40（训练权重 20），

   **以后某个桶仍顽固时，先看权重注入比例，再决定补样本还是提 count。**

## 6.5 摘要丢弃实验（最重要的方法论收获）

**现象**：`交货 - C000425,深圳麦哲科技` 被判采购，而 `发出商品[借]+库存商品[贷]`
在金标准里 3,874 count **100% 是成本结转**。

**探针**（固定同一科目组合，只改摘要）：

| 摘要 | 判断 |
|---|---|
| `发出商品--某客户` | 成本结转 1.000 ✅ |
| `结转本月发出商品` | 成本结转 1.000 ✅ |
| `交货` | 采购 1.000 ❌ |
| 中性文本「本月合计」 | 采购 0.99 ❌ |

**结论：模型认的是"发出商品"这四个字，不是科目组合。** 一旦摘要没有提示词，就掉回先验
（采购是最大桶），组合完全拉不回来。

**做法**：训练时按概率把摘要置空，堵死"背摘要"这条捷径。

| 测试集 | 对照（0） | 丢弃 0.3 |
|---|---:|---:|
| A 交货措辞（120 条，训练集从未出现的说法） | 26.7% | **99.2%** |
| B 中性文本（846 条，只给科目组合） | 13.1% | **32.2%** |
| C 常规验证（2,000 条） | 93.8% | 94.0% |

B 组关键桶（只给组合不给摘要）：

| 桶 | 对照 | 丢弃 0.3 |
|---|---:|---:|
| 成本结转 | **0/30** | **28/30** |
| 生产制造 | 6/30 | **30/30** |
| 费用·办公 | 0/30 | 2/30 |

**丢弃率扫描**：

| 丢弃率 | A | B | B·成本结转 | B·生产制造 | C | val_acc |
|---:|---:|---:|---:|---:|---:|---:|
| 0 | 26.7% | 13.1% | 0/30 | 6/30 | 93.8% | 93.87% |
| 0.2 | 98.3% | 24.5% | **0/30** | 20/30 | 94.2% | 93.91% |
| **0.3** | **99.2%** | 32.2% | 28/30 | 30/30 | 94.0% | 93.89% |
| 0.4 | 98.3% | **37.1%** | 28/30 | 30/30 | 94.2% | 93.95% |

**读法**：0.2 是坑——措辞救回来了但组合仍是 0/30，它靠残留文字线索在猜。
**0.3 是拐点**（组合真正学会），0.3 与 0.4 实质打平，取 0.3（干预更小、A 组略好）。
常规准确率三者都在 94% 左右，**丢弃没有代价**；唯一代价是收敛慢半拍。

## 6.6 指标口径的坑

`per_bucket_accuracy` 是**按 count 展开后的样本级**准确率。一条 count=12 的记录，
在验证集里就是 12 条一模一样的样本。

投资桶 52 条验证样本里有 12 条是同一条记录（`收中国证券登记结算…派发红利代扣个税`），
它一错，投资就掉 23 个百分点——**记录级实际是 92.5%**。

**规则：以后看分桶指标，必须同时看样本级和记录级。** 小桶（<20 条验证样本）的单点准确率
没有统计意义，要看混淆矩阵；v10 那批"100%"的桶只有 5–6 条验证样本，不可比。

**还有一类更隐蔽的口径错误：在展开样本上再乘一次 count。** `split_records` 返回的验证集
已经按 `min(count,20)` 复制过，若再按 `count` 加权求和，得到的是 **count²**：

| 口径 | 验证集错误量 |
|---|---:|
| 展开样本上再乘 count（错） | 6,796 |
| 展开样本直接计数（= 训练权重） | 518 |
| 去重到记录后按 count 求和 | **582** |

放大近 12 倍，导致"某科目组合错误 640"比该组合在金标准里的总量（4 条 / 54 count）还大——
这种自相矛盾的数字应当在写下来的那一刻就发现。**规则：报错误量时先声明口径
（记录数 / 展开样本数 / 训练权重），三种不混用。**

## 7.1 单一数据源

`config.BUCKET_REGISTRY` 不再手写，改为从 `assets/bucket_taxonomy_v10.json` 派生

## 7.2 别名重定向

模型输出的是重训时的桶名。桶改名后（如"银行手续费→结算手续费"），
旧模型仍输出旧名，靠 `merge_alias_probs` 在**温度校准之前**把概率并入新名。

`index_to_bucket.json` **绝不能手工改**——那是模型的输出映射，重训后才会变。

## 7.3 I/O 与数据格式（2026-11-09）

| 项 | 改前 | 改后 |
|---|---|---|
| xlsx 读取 | openpyxl（10.3s / 64k 行） | **calamine（Rust）2.5s**，失败回退 openpyxl |
| .xls | **读不了**（openpyxl 不支持） | 可读 |
| 中文 CSV（GBK） | `UnicodeDecodeError` | utf-8-sig → utf-8 → gb18030 回退 |
| 输出 | 一律 openpyxl | ≤50 万行 xlsx（xlsxwriter）；>50 万行 **CSV** |

为什么是 50 万：Excel 单表硬上限 1,048,576 行，留 4 倍余量避免用户二次加工后溢出。
硬写 xlsx 会静默丢行。

格式实测（64,255 行 → 200 万行推算）：

| 格式 | 写 | 读 | 体积 |
|---|---:|---:|---:|
| Feather | 2.1s | — | 4.2MB |
| **Parquet** | 6.6s | 3.6s | **1.2MB** |
| CSV | 10.7s | 5.9s | 18.1MB |
| SQLite | 11.8s | 11.6s | 20.3MB |
| xlsx | **467s** | 270s | 7.2MB |

内部落盘用 Parquet（小 15 倍、保留科目编码前导零）。**输入侧不做预转换**——
一份文件一次会话只读一遍，转换是纯支出。

| | 全年账（1 家） | 大账（8 家） | 倍数 |
|---|---:|---:|---:|
| 行 | 64,255 | 846,991 | 13.2× |
| 凭证 | 11,456 | 144,119 | 12.6× |
| 读表 | 1.7s | 11.2s | 6.6× |
| 模型调用 | 5,112 | 46,365 | 9.1× |
| 端到端 | 10.96s | **95.6s** | 8.7× |
| 内存峰值 | ~1.2GB | 2.63GB | 2.2× |

端到端只涨 8.7 倍而行数涨 13.2 倍：去重比随公司数上升（2.22 → 3.55），
模型调用只涨 9.1 倍；读表、写回这些按行计的固定开销被摊薄。

**验收口径**：11,456 张凭证的「业务分类 + 置信度」与上一版逐条对拍差异 97 张（0.85%），
抽检多为纠正（§6.4）。

**关键认识一：去重是 25:1**（行 → 凭证 5.7:1，凭证 → 记录 4.4:1），模型调用量远小于行数。
200 万行对应约 35 万次模型调用，去重后约 16 万次。

**关键认识二：模型是唯一随规模线性增长且无法绕开的开销**。全年账占 63%，
大账占 55.8%——比例下降不是因为模型变便宜，而是去重比从 2.22 涨到 3.55、
调用量只按 9.1 倍增长。硬约束向量化后降到 1.8%，读表与去重各占约 12%。
唯一能超过模型的单项是训练数据导出（大账 110s / 46.6%），现已默认关闭——
普通用户只跑账不训练，需要样本时用 `SUMMARY_CLEANER_EXPORT_TRAINING=1` 显式开启。

**关键认识三：GPU 与 CPU 的耗时结构完全不同**。GPU 上模型占 55–63%，CPU 上占 90% 以上
（int8 量化后 96 条/秒，同规模约 53 秒）。面向财务用户的部署形态是 CPU，
性能决策必须以 CPU 为准（见 §4.6.8）。

## 7.5 Rust 决策（结论：不重写）

| 项 | 实测/推算 |
|---|---|
| 引擎（读+写+逐行）占 200 万行总时长 | 向量化前约 85%，**向量化后约 50%** |
| Rust 理论上限 | 向量化前 4–6×，**向量化后仅 1.27×** |
| 换 bge-base（需重训） | 1.2×（40.8s → ≈34s） |
| **真正该先做的向量化** | **已完成（2026-11-09，81.3s → 40.8s）** |

`calamine` 的 91% 时间花在"把 Rust 对象转成 Python 对象"（解析本身 0.10s，转对象 0.96s）。
**"原生 Rust 更快"只在全程不落地 Python 对象时成立**，即 PyO3 扩展形态：
Rust 负责解析 → 归一化 → 指纹 → 聚合 → 写盘，只把结果交回 Python。

触发条件（写死，别凭感觉）：向量化之后 ETL 仍 >50%，或需要单进程 >500 万行。
**现状：向量化后 ETL 已降到约 6s/40.8s（15%），触发条件不成立。**

## 7.6 三层复用，别混为一谈

| 层 | 复用条件 | 复用对象 | 收益 | 状态 |
|---|---|---|---|---|
| dedup 结论复用 | 同科目组合 + 摘要相似 | 桶 + 置信度 | **2.22:1**（-55%） | 已上线（§4.6.2） |
| 编码复用（同轮） | 归一化摘要相同，科目可不同 | 1024 维向量 | **2–3%** | 已上线（§4.6.3） |
| 结果缓存（跨轮） | 摘要 + 科目都相同 | 桶 + 置信度 | 同账再跑 100% | **不做** |

三点要说清：

1. **同轮的主力是 dedup**（2.22:1），编码复用只补最后 3%——因为一笔业务通常就是一个
   科目组合，同一句话配两三种科目的情况很少（121 组 / 4,949 种摘要）。
2. **跨轮用结果缓存就够了**，不必用编码缓存：同账再跑两者都是 100%，而结果缓存更彻底
   （连分类头一起省）。编码缓存的落盘是实现的副产品，不是设计目标。
3. **摘要完全重复率只有 2.8%**，这是所有"按摘要缓存"方案的共同天花板——真实摘要带客户名、
   单号、月份，天然不重复。跨轮能到 100% 只是因为跑的是同一份账。

## 9.2 标注冲突检查（`_dev/scripts/check_label_conflicts.py`）

| 层 | 键 | 冲突 | 说明 |
|---|---|---:|---|
| L0 精确 | 去空白摘要 + 科目组合 | **0 组** | 同键不同桶一定是错标 |
| L1 掩码 | 数字掩码摘要 + 科目组合 | 14 组 / 66 count | 剩余均为"费用父级 vs 子桶"或真模糊 |

L0 从 1 组降到 0、L1 从 22 组 / 209 count 降到 14 组 / 66 count，靠的是 2026-11-06
那轮修正（19 条 / 80 count）。

> **教训**：业务动词（"到期""回款""结算"）本身不含方向，规则必须看借贷方向。
> 一条"含汇票到期且桶=采购 → 销售"的规则差点把 552 count 的**付**货款挪走，
> 因为 `应付票据[借]+银行存款[贷]` 也含"汇票到期"。预演救回来了。

## 9.3 三组评测（`_dev/scripts/eval_ood_wording.py`）

| 组 | 看什么 | 底线 |
|---|---|---|

# 十、已知问题

## 10.1 桶层面

| 问题 | 现状 |
|---|---|
| `应交税费[借]+银行存款[贷]` 跨两个桶（进口→采购、国内→税费） | 已接受，靠税种词区分 |
| 长尾桶组合数偏少（存款利息 16、政府补助 21、筹资费用 22） | 仍是最脆弱处；筹资费用准确率 **65.4%** 为全库最低 |
| 组合准确率为 0% 的桶（结算手续费、押金保证金、筹资费用、存款利息、单位往来、员工借支） | 科目组合与邻近桶同形，只能靠摘要措辞区分（§2.5） |
| `费用 ↔ 采购` 互为最大错向（28 / 19 条） | 边界是"这笔钱买的是服务还是货物"，需要更细的措辞覆盖 |

## 10.2 模型层面

| 问题 | 现状 |
|---|---|
| 高置信档仍有 **2.94%** 判错（128 / 4,355 条记录） | v10.3 为 4.33%；这是"最大系统性错误"的水平，靠补样本改善，不靠调温度 |
| 费用 ↔ 费用子桶互串 | 已随子桶合并消失 |
| 对抗样本 `count=1`，相对高频正例（count 到 40）权重极低 | 费用/采购实际只注入 1.6%，某桶顽固时先提 count 再考虑补样本（§6.4） |
| `per_bucket_accuracy` 为样本级 | 小桶指标会失真，需同时看记录级（§6.6） |

## 10.3 工程层面

| 问题 | 现状 |
|---|---|
| **模型是主要瓶颈** | GPU 上模型占 55–63%（全年账 63.3% / 大账 55.8%），CPU 上 90%+（§7.4） |
| GPU 利用率仅约 30% | 差距在小 batch 的 kernel launch，Python 侧已无空间 |
| 结果缓存上限 2.8% | 摘要天然不重复；摘要**编码**缓存已上线（§7.6） |
| 混合到账未自动拆两笔 | 落待复核，需改 `cf_by_row` 数据结构 |
| `fallback_parent` 空转 | 唯一父子关系随子桶合并消失，规则无触发对象（§5.4） |
| `stats.sim_deduped` / `stats.buckets` 描述的是上次 build 的状态 | 手工注入样本后不会更新，别当实时值 |
