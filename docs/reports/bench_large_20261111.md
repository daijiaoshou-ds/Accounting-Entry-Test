## 三、两个新暴露的瓶颈

### 3.1 训练数据导出成了最大头（冷跑 46.6%，热跑 58%）

导出流程：143,271 条记录 → 精确去重 70,217 条 → 相似去重 49,817 条 → **23,237 条**落盘。

`_dedupe_similar_summaries` 原本对组内每对摘要都跑一次完整 `difflib.ratio()`（O(n²) 字符级 LCS），
在 14 万条量级上吃掉了 pipeline 近八成时间。加三级预筛后（长度比 / `real_quick_ratio` /
`quick_ratio`，三者都是 `ratio()` 的数学上界，**不改变判定结果**）：

| | 优化前 | 优化后 |
|---|---:|---:|
| pipeline 总耗时 | 486.0s | **225.4s** |
| 训练导出 | ~370s | **110.5s** |
| 导出结果 | 23,237 / 49,817 / 70,217 | **完全相同** |

优化后它仍是最大单项——因为 14 万条记录两两比较的规模摆在那里。

### 3.2 硬约束逐凭证扫描（28–30s，12–16%）

`hard_rule_vouchers` 对每张凭证扫一遍科目集合，15 万凭证 = 28s。单公司账（1.1 万凭证）时
只有 2.2s，不显眼；大账上成了第二大项。可以向量化（把科目矩阵化后整表匹配），
预计能压到 3–5s。

## 五、数据质量问题：一家公司的摘要是空的

未分类 5,830 张里，**5,222 张是摘要为空**，其中 **5,221 张全来自 `序时账5.xlsx`**：

| 来源 | 凭证数 | 无摘要 |
|---|---:|---:|
| 序时账5.xlsx | 74,105 | **5,221** |
| 序时账8.xlsx | 21,976 | 1 |
| 其余 6 个 | 53,878 | 0 |

无科目凭证 0 张，科目全不在词表的凭证 0 张——所以这些不是模型能力问题，
是源文件那家公司的摘要列没导出。**这类凭证目前只能落「未分类」，进复核清单。**
