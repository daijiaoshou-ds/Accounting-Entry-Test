## 二、需要修的缺陷

### B-4【高·已修复】Excel数据提取：保存必失败（用户实测）

- **现象**：点「开始提取」→ `保存失败: Cannot save file into a non-existent directory: ...\_work\excel_extract\output`
- **位置**：`other_tools/web/excel_extract.py` 的 `run_clicked` 分支
- **根因**：页面只 `mkdir` 了 `input`，**没有创建 `output` 目录**，却把 `output/提取结果.xlsx` 直接交给
  底层 `to_excel()` / `write_csv()` —— pandas 不会自动创建父目录。
- **修复**：抽出 `prepare_run(is_csv)` 统一建目录并返回 `(输入目录, 保存路径)`，
  页面与测试共用同一套目录约定，避免再次不同步；同时抽出 `output_path(is_csv)` 供下载区复用。

### B-5【中·已修复】PDF索引号生成：一上传就崩（用户实测）

- **现象**：点「添加索引」→ `任务异常: TypeError: unsupported operand type(s) for +: 'WindowsPath' and 'str'`
  （`modules/pdf_indexer.py` 的 `file_path + ".tmp"`）
- **根因**：`_common.save_uploaded()` 返回的是 **`Path` 对象**，而原桌面版模块全是按 **`str` 路径**写的。
  同一处不一致还有第二个炸点：页面 `_run` 里 `dst = out_dir / os.path.basename(src)`，
  当 `out_dir` 被传成 `str` 时引爆 `TypeError: unsupported operand type(s) for /: 'str' and 'str'`。
- **修复**：`save_uploaded()` 统一返回 `str`（并补 `target_dir.mkdir(parents=True, exist_ok=True)`）；
  页面 `_run` 内部 `out_dir = Path(out_dir)`、`src = str(src)`，目录拼接用 Path、传给桌面模块一律 str。

### B-6【高·已修复】PDF索引号生成：文件被占用时整个任务以异常收场

- **现象**：Windows 下偶发 `PermissionError: [WinError 32] 另一个程序正在使用此文件 ... doc.pdf.tmp`，
  且**异常逃出 `_run` 直达后台任务层**（页面显示「任务异常」而不是「失败: xxx」）
- **根因**：`modules/pdf_indexer.py` 的 `except` 块里 `os.remove(temp_path)` 位于 try 之外，
  当 `.tmp`（保存字体后约 18 MB）被杀软/索引服务短暂占用时，**该 remove 再次抛异常**，
  把「replace 失败」这个真实原因整个吞掉并向上逃逸。
- **修复**：新增 `_robust_replace()`（有限次退避重试 `os.replace`）
  与 `_silent_remove()`（尽力清理、被占用则静默跳过），
  `except`/`finally` 里的 `doc.close()` 也各自加保护。`stop_event` 分支的清理同样改用 `_silent_remove()`。
- **实测**：修复前该路径 100% 以异常逃逸收场；修复后连续 12 次运行 **成功 12 / 失败 0 / 逃逸 0**。

### B-7【中·已修复】PDF合并页面：一进页面就报「页面加载失败」

- **现象**：`「PDF合并/分拆/转换」页面加载失败：'str' object has no attribute 'name'`
- **根因**：**B-5 的连带影响**——`save_uploaded()` 改为返回 `str` 后，
  `pdf_merger.py` 里 `files.sort(key=lambda p: p.name.lower())` 仍按 `Path` 取 `.name`。
- **修复**：改为 `key=lambda p: os.path.basename(p).lower()`，并对全部 `save_uploaded` 调用点做了审查
  （`grep saved|files.sort|save_uploaded` 确认无其他残留）。

### B-8【中·已修复】Excel格式互转：转换成功却显示红色报错

- **现象**：`_run_upload` 返回「转换完成。成功: 1, 失败: 0」并出现下载按钮，但页面同时弹出**红色 error 提示**
- **根因**：判断逻辑 `if ok and "成功" in msg.split("。")[0]` ——
  `msg.split("。")[0]` 是 `"转换完成"`，永远取不到「成功」二字，于是把成功当失败展示。
- **修复**：改为 `has_success = ok and "成功" in str(msg)`。

## 三、已确认「不是 bug」的观察项（无需改）

### B-1【中→已修复】PDF合并：Excel/图片转PDF 首次点击必然失败

- **位置**：`other_tools/web/pdf_merger.py` 的 `_ensure_font_asset()` + `other_tools/modules/pdf_merger.py` 的 `core_merge_process()`
- **现象**：勾选「转换 Excel/图片 并合并」→ 点开始合并 → 报 `错误: 缺少字体文件 simsun.ttc`
- **根因**：项目根目录**原本没有** `assets/fonts/simsun.ttc`（这是原桌面版「基米工具箱」的打包资源，迁移时未带过来）。
  字体只在用户**点击按钮那一帧**由 `_ensure_font_asset()` 从系统字体复制，所以第一次点击时 `core_merge_process()`
  内部的字体检查先失败、直接返回「缺字体」；**第二次点击才成功** —— 典型的「第一次莫名其妙失败、第二次就好了」。
- **实测**：`test_run_smalltools.py::5.6a`（临时移除字体模拟首次部署）稳定 FAIL；
  `5.6b`（先调用一次 `_ensure_font_asset()`）PASS，证明兜底逻辑本身有效。
- **处置**：已把系统字体复制到 `assets/fonts/simsun.ttc`（18 MB），**当前环境该问题已消失**。
  `start.bat` 会 `cd /d "%~dp0"` 再启动，工作目录即项目根，因此字体路径可稳定命中。
  > 后续若仓库体积敏感，可改为「打包/部署时自动复制系统字体」，或在 `_ensure_font_asset()` 中把提示
  > 改成「正在准备字体资源，请再点一次开始合并」以免用户误判为故障。
- **回归**：`test_run_smalltools.py::5.6b`。

### B-2【高】银行流水匹配：同一凭证同科目多行银行存款会被丢行（影响未匹配明细准确性）

- **位置**：`bank_statement_matcher/src/core/journal_opponent_analysis.py::_split_simple()`
- **根因**：函数只用 `bank_rows.iloc[0]` 当模板，然后按对方科目行数复制。当一张凭证里**同一个明细科目有多行银行存款**时，
  其余银行行的金额被丢弃，行数被「对方科目行数」覆盖。
- **实测**（`probe_bank_behavior.py` 探针 A）：

  ```
  输入：银行存款/工行 借 500  +  银行存款/工行 借 300  +  应收账款 贷 800
  输出：银行存款/工行 借 800  客商 甲        ← 只剩 1 行，500/300 的拆分丢失
  期望：银行存款/工行 借 800  客商 甲（金额需与银行侧 2 笔 500/300 各自对应）
  ```

  金额合计虽正确，但**颗粒度丢失**：银行侧若为两笔（800 或 500+300），GL 侧只剩一条 → 未匹配明细表无法定位是哪一笔未达，
  月度差异表也无法按笔核对。诊断面板里「序时账各明细科目月度分布」的笔数同样偏小。

### B-3【中】银行流水匹配：多银行账户拆分时「客商未按金额配对」

- **位置**：`journal_opponent_analysis.py::_try_split_multi_bank()`
- **根因**：该函数只校验「金额能否一一对应」，命中后直接复用 `bank.to_dict()`，**没有把配对的客商写回行里**；
  后续 `clean_journal` 从客商列解析 `counterparties`，于是拿到的是空客商。而 `docs/Modify.md:167-177` 明确要求：
  「供应商A的100对应建行001的100 …… 让它变成一对一的标准借贷会计分录」。
- **实测**（探针 C）：

  ```
  输入：工行 借300 + 建行 借700 / 其他应收款 贷300(甲) + 贷400(乙)
  实际：工行 借300 客商=甲，乙 ；建行 借700 客商=甲，乙   ← 客商串用
  期望：工行 借300 客商=甲   ；建行 借700 客商=乙
  ```

  影响：名称模糊匹配（`NameVectorizer`）这一维度失效，只能靠金额匹配，降低疑难款项的匹配率。
  对比之下，不满足一一对应的退化分支（探针 D）行为**符合设计**（每行带全部客商）。
