> 版本 3.0：微调 BGE 中文 Embedding 模型做凭证业务分类（推翻 Pattern×Keyword + Triplet 旧架构）。
> 理论设计见 [NN_training2.0.md](./NN_training2.0.md)；配套引擎见 [technical_report2.1.md](./technical_report2.1.md)（V2.1 规则引擎）。

## 一、架构总览

### 1.1 核心思路

旧版 NN（Pattern×Keyword + Triplet Loss 聚类）从 0 训练，模型**不懂中文**："付杭州分公司货款"→存货采购是背答案，"付北京分公司货款"就懵。

V3.0 改为**微调中文预训练模型 BGE-Large-zh-v1.5**（已懂中文语义），输入改为「整句摘要 + 科目开关向量」，输出桶概率（CrossEntropy 分类，非聚类）。

### 1.2 完整前向公式

$$\text{logits} = \text{Head}\Big( \text{CLS}\big(\text{BGE}(summary)\big) \;\oplus\; \text{Linear}_{64}(switch) \Big)$$

$$\hat{y} = \arg\max_b \; \text{softmax}(\text{logits})_b$$

| 分量 | 维度 | 含义 | 来源 |
|------|------|------|------|
| $\text{BGE}(summary)$ | 1024 | 摘要整句的语义向量（last_hidden_state 第 0 位 = [CLS]） | 预训练 BGE-Large-zh-v1.5 |
| $switch$ | 130 | 科目开关 one-hot（一级科目[方向]，如 `应付账款[借]`） | 凭证科目行 |
| $\text{Linear}_{64}$ | 130→64 | 科目开关压缩投影 | 可训练（head 组） |
| $\text{Head}$ | 1088→256→$B$ | 分类头：Linear(1088,256) → ReLU → Dropout(0.1) → Linear(256, B) | 可训练（head 组） |
| $B$ | 17 | 业务桶数 | 金标准动态构建 |

**Loss**：$$\mathcal{L} = -\log \frac{e^{z_{y}}}{\sum_b e^{z_b}} \quad (\text{CrossEntropy})$$

### 1.3 数据流总览

```
序时账 → V2.1 引擎分类（Step 9 自动导出）
       → training/unreviewed/{hash}.json（buckets_v2 格式）
       → 置信度主动学习（high 自动并入金标准，AI 不读）
       → AI 审核（只删不改）→ merge → training_data.json（唯一金标准）
       → split_records() 80/20 按桶分层
       → FinanceClassifierTrainer.train()（微调 BGE）
       → 4 件交付物 → FinanceClassifierInference.predict()
```

## 二、数据流水线

### 2.1 训练记录提取

按凭证号分组，聚合摘要（非空去重、空格拼接、**上限 200 字符**），科目提取方向：

| 行方向 | 判定 | 科目开关 |
|--------|------|---------|
| 借方金额 > 贷方金额 | 借 | `应付账款[借]` |
| 贷方金额 > 0 | 贷 | `银行存款[贷]` |

> 踩坑：NaN 的 truthy 陷阱——`x or 0` 无法转换 NaN（`bool(nan) == True`），导致 85% 记录只剩贷方。修复：`pd.to_numeric(errors="coerce")` + `pd.isna` 显式判断。

**硬规则桶**（绝不进入训练）：`HARD_RULE_BUCKETS = {其他业务, 资金内部往来, 汇兑损益}`——由 V2.1 代码 if 语句写死分配，无学习价值。

### 2.2 相似摘要去重（-80.5%）

同一业务按月重复（"付XX公司货款"），数字不同语义相同。处理流程：

1. **数字归一化**：摘要中所有数字 → `#`（日期/凭证号/金额对分类无意义）
2. **difflib SequenceMatcher** 相似度 ≥ 75% → 合并，count 累加

> **算例**：`付杭州分公司货款 2025年1月` → `付#分公司货款 ####年#月`；`付杭州分公司货款 2025年2月` → 归一化后相同 → 合并为 1 条，count=2。同时"付北京分公司货款"归一化后 ≠ 杭州版 → 保留两条（模型学到的是"付X分公司货款"的桶归属，这正是泛化目标）。
>
> 实测：9966 → 1947 条（-80.5%）。

### 2.3 置信度主动学习

AI 审核成本高，程序先筛掉已确认的：

| 判定 | 条件（与金标准 golden 比对） | 去向 |
|------|------|------|
| **high** | subjects 完全相同 + bucket 相同 + 摘要相似度 ≥ 75% | 直接并入金标准，**AI 不读** |
| **low** | 其余 | 主文件 `{hash}.json` → AI 审核 |

### 2.4 merge 幂等（金标准唯一性）

- `source_hashes` 字段跟踪已消费文件 → 重复运行不重复并入
- 同 key（摘要+科目+桶）跨文件 count 累加；同 key 不同桶 → count 加权众数胜出
- **关键顺序**：先读现有金标准 → 再构建合并结果（曾因顺序错误导致金标准被空数据覆盖，修复后幂等验证通过）

### 3.2 本次迭代的桶改造

| 改动 | 内容 | 边界设计 |
|------|------|---------|
| 费用报销 → **日常费用** | 改名统一语义 | 报销只是日常费用的一种确认方式 |
| 新增 **员工借款** | Step 0d 硬规则 | `其他应收款[借]` + 借款/借支/暂借/暂支 + 排除{公司,单位,集团,往来} |
| 新增 **单位往来** | 兜底桶 | clarity 1.0（全桶最低），仅"往来款/暂收/暂付"关键词加分 |
| 研发修正 | 110 条误分类移入 | 研发测试认证费(96)+研发领料(14)，按"一切与研发有关的活动"定义 |

> **员工借款 vs 借款筹资的数学本质**：裸关键词"借款"→借款筹资 +0.8（KEYWORD_EXPLICIT_SCORES）。但科目是 `其他应收款[借]`（员工挂账）时业务是员工借款；银行借款科目是短期/长期借款[贷]，不会出现其他应收款[借] → Step 0d 用**科目+摘要联合判定**，规则安全（冒烟 10/10 通过）。
>
> **单位往来 vs 押金保证金**：两者都锚定其他应收款。区分靠关键词（往来款 vs 押金/保证金）+ clarity 优先级（单位往来 1.0 < 押金 2.0）——"付XX往来款"只有往来款命中 → 单位往来胜；"付XX押金"无往来词 → 押金胜。

## 四、训练方法

### 4.1 三策略

| 策略 | 机制 | 适用 |
|------|------|------|
| full（默认） | 编码器 + 分类头全部可训练 | 8GB 显存 + batch≤4 |
| lora | peft `LoraConfig(r=16, lora_alpha=32, target=["query","value"])` + `enable_input_require_grads()` | 显存紧张，质量接近 |
| frozen | 编码器 `requires_grad=False` | 最快最省，冒烟验证 |

### 4.2 参数速查（踩坑后定稿）

| 参数 | 值 | 踩坑记录 |
|------|-----|---------|
| `NN_ENCODER_LR` | **1e-5**（初版 2e-5） | 2e-5 时 Epoch 2 验证准确率 95.4%→87.1% 崩盘——预训练权重被大步长推离最优区域 |
| `NN_HEAD_LR` | 1e-3 | 分类头随机初始化，需快收敛 |
| LR 调度 | warmup 10% + 线性衰减 | `get_linear_schedule_with_warmup(warmup=0.1×total_steps)`，微调标准做法 |
| `NN_DEFAULT_EPOCHS_V3` | **8**（初版 20） | 预训练模型 1-3 轮即收敛，20 轮 17 轮白跑（每轮 ~13 分钟） |
| batch | 4 | 8GB 显存实测 ~6.5GB；3 线程并发 19GB → OOM（已加防重入锁） |
| `max_length` | 64 tokens | 压显存；摘要 200 字符截断 |
| 早停 patience | 5 | 连续 5 轮无提升停止，保存历史 best |
| 数据划分 | 80/20 按桶分层 | `split_records(seed=42)`，避免小桶全进验证集 |

### 4.3 显存优化三件套

1. **fp16 AMP**：`torch.amp.autocast(cuda, float16)` + `GradScaler`
2. **gradient checkpointing**：`encoder.gradient_checkpointing_enable()` + `use_cache=False`
3. **短序列截断**：`max_length=64`

8GB 笔记本 GPU（RTX 4060 Laptop）实占 ~6.5GB。

### 4.4 早停（为什么"第一轮最好"不是 bug）

$$\text{best} = \arg\max_{e} \text{val\_acc}_e, \quad \text{stop if } e - \text{best\_epoch} \geq 5$$

预训练模型已懂中文：第一轮微调就"校准到位"（分类头拟合 + 编码器轻调），之后每轮编码器继续偏离预训练最优区域 → **背训练数据**（train_loss 降、val_acc 崩）。数据量（万级）远小于模型容量（326M 参数）时这是必然现象，早停就是保护。

### 4.5 工程防护（生产可靠性）

| 机制 | 作用 |
|------|------|
| 后台线程 + `training_progress.json` | 训练不阻塞页面，每轮写进度，前端 `st.fragment(run_every=2.0)` 刷新 |
| 防重入锁 `_TRAIN_LOCK` | 任何时刻仅一个训练线程（3 线程并发 OOM 事故后新增） |
| 显存自检 | 可用 <5.5GB 直接报错（而非跑几秒后 OOM） |
| 秒级停止 | 每 batch 检查 stop 信号，点停止秒级生效，best 已保存 |
| 残留清理 | 进程重启后清理 running 状态的残留进度文件（防无限整页刷新） |

## 五、实验与结果

### 5.1 三版对比

| 版本 | 数据 | 配置 | best val_acc | 曲线行为 |
|------|------|------|:---:|------|
| v1 | 2005 条/15 桶 | LR 2e-5，无 warmup | **97.87%**（Epoch 2） | 数据少，过拟合慢 |
| v2 | 13599 条/15 桶 | LR 2e-5，无 warmup | 95.4%（Epoch 1） | Epoch 2 崩至 87.1%——过拟合信号明显 |
| v3 | 13818 条/17 桶 | LR 1e-5 + warmup + epochs 8 | **95.8%**（Epoch 2，仍在上升） | 曲线健康，过拟合缓解 |

### 5.2 关键结论

- **LR 1e-5 + warmup 的收益可量化**：v2 的 Epoch 2 崩盘（-8.3 点）→ v3 的 Epoch 2 上升（+1.0 点）
- **95.8% < 97.87% 不是退步**：验证集几百条 → 2766 条（题目变难），17 桶 > 15 桶（类别更多）
- 泛化验收通过：同科目组合下"付杭州分公司货款"与"付北京分公司货款"预测同一桶

### 5.3 新桶冒烟（V2.1 规则引擎，10/10）

| 输入 | 科目 | 预测 | 正确性 |
|------|------|------|:---:|
| 付深圳市宏远科技有限公司往来款 | 其他应收款[借] | 单位往来 | ✅ |
| 张三借款回家过年 | 其他应收款[借] | 员工借款 | ✅ |
| 李四借支小孩上学费用 | 其他应收款[借] | 员工借款 | ✅ |
| 王五借备用金出差 | 其他应收款[借] | 日常费用 | ✅（备用金不抢） |
| 借款给XX公司 | 其他应收款[借] | 借款筹资 | ✅（公司词排除） |

## 六、推理

### 6.1 4 件交付物

| # | 文件 | 说明 |
|---|------|------|
| ① | `fine_tuned/` | 微调后 BGE（fp16，~650MB，save_pretrained） |
| ② | `finance_classifier.pt` | 分类头权重 + 元数据（best_val_acc/epoch/num_subjects/num_buckets） |
| ③ | `subject_to_index.json` | 科目开关索引（130 个） |
| ④ | `index_to_bucket.json` | 桶索引（17 个） |

加载校验：`num_subjects` 不一致 → 报错不静默。

### 6.2 未知科目处理

$$\text{switch}_i = \begin{cases} 1 & \text{科目} i \in \text{subject\_to\_index} \\ 0 & \text{未知} \end{cases}$$

未知科目开关保持 0 + 收集 `unknown_subjects` 警告——**不扩容**（扩容破坏已训练权重），提示补充训练数据后重训。

> 踩坑：输入 `[借方]`/`[贷方]` 与索引 `[借]`/`[贷]` 不匹配 → 误报 unknown。修复：`_normalize_subject()` 归一化 `[借方]→[借]`、`[贷方]→[贷]`。

## 七、关键设计决策

| 决策 | 理由 |
|------|------|
| 微调预训练模型而非从 0 训练 | 中文语义零成本继承，"付杭州/付北京"天然同桶 |
| 科目开关 one-hot 而非序列输入 | 科目是"开关"不是"文本"——组合出现即业务模式 |
| 整句摘要（弃用 jieba 分词） | 预训练模型自带语义切分，词边界由 BERT 式 tokenizer 处理 |
| 相似去重 75% 阈值 | 数字归一化后，同类业务合并；阈值过低合并不同业务 |
| 置信度主动学习 | AI 只审最难部分，审核成本与数据量解耦 |
| 硬规则桶不进训练 | 机械性凭证无学习价值，还污染分布 |
| 未知科目不扩容 | 扩容破坏已训练权重；收集警告驱动数据补充 |
| early stop + 低 LR | 预训练模型微调的核心保护：不偏离最优区域 |

## 八、已知局限

1. **类别不均衡**：存货采购 9475 vs 分红股利 6——模型对 6 条样本的桶近乎随机。专项补数据是最大杠杆
2. **新桶零样本**：单位往来、员工借款桶无训练样本（V2.1 已能分对，等跑新数据后审核并入）
3. **auto 数据噪声**：置信度 high 直接并入金标准的记录可能残留 V2.1 错误标签
4. **"第一轮最好"的固有限制**：数据量（万级）远小于模型容量（326M），后续轮次提升空间有限
5. **长摘要截断**：max_length=64 丢弃长摘要尾部信息（多为供应商/日期细节，影响有限）
6. **GBK 控制台**：Windows 终端 print 不能含 emoji（页面内不受影响）
