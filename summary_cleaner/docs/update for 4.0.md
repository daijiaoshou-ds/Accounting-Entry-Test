## 版本更新

此前这个功能经过了3次更新，现在我打算进行第四次更新。

## 当前版本面临的问题：太慢

从技术报告里可以看到，我们把训练好的模型分为了GPU版和CPU版本。

其中，CPU版本是大多数我们的用户安装的版本，但CPU版本很慢，我们现在想一想提速的方法。

## 如何去提速？

### 1. 将序时账按照<科目组合>进行切割

在我们原来的设计里，本来就是有科目组合这个概念的，科目组成它长这样：

```json
      {
        "subjects": [
          "短期借款[贷]",
          "银行存款[借]"
        ],
        "records": [
          {
            "summary": "2025/12/24贷款入500万-利率2.3%",
            "count": 4
          },
          {
            "summary": "公司向银行贷款1000万元",
            "count": 3
          },
          {
            "summary": "2025/10/8-入2000万供应链融资贷款-2.2%",
            "count": 2
          },
          {
            "summary": "收到中行贷款放款2000万，期限：2023.6.30-2024.6.30，利率2.8%",
            "count": 2
          },
          {
            "summary": "收到中行（3798）贷款3000万放款，利率2.8%，期限20230310-20230828",
            "count": 2
          },
          {
            "summary": "2025/8/15-入福费廷贷款2000万",
            "count": 1
          }
        ]
      },
```

一份科目组合里，包含多个摘要。

这就是意味着，我们可以把一份序时账进行切割。

比如，一份序时账里，有1万张凭证：

- 老版本：我们要用训练好的模型，去逐张判断
- 我预想的新版本：将1万张凭证分割为科目组合和摘要

模型只需要去判断这个[科目组合]+[摘要]应该归类到什么业务活动就行，它不需要逐张凭证去判断，这会大大减少它的判断工作量。

### 2. 对相似的摘要进行去重

比如，我们上面"短期借款[贷]","银行存款[借]"的这个组合，出现了一个新的这样的摘要：

```json
      {
        "subjects": [
          "短期借款[贷]",
          "银行存款[借]"
        ],
        "records": [
          {
            "summary": "公司向银行贷款1000万元",
            "count": 4
          },
          {
            "summary": "公司向银行贷款2000万元",
            "count": 3
        ]
      },
```

我们没必要去判断这段新的部分，因为向银行贷款2000万元和向银行贷款1000万，本质是同一个业务活动。

也就是说，在同一个科目组合里，我们可以对很相似的摘要进行去重，这样可以二次减少模型判断的工作量。

模型只需要去判断"短期借款[贷]","银行存款[借]"+"公司向银行贷款1000万元"是什么业务活动，然后"短期借款[贷]","银行存款[借]"+"公司向银行贷款2000万元"就会去抄“贷款1000万元”的“作业”，不用经过模型判断。

同时，再把判断结果“写回”每份凭证里。

去重的关键：

- 不要看数字：我们忽略掉文本里的数字。原因是，数字不影响文本的语义，比如，贷款100万元和贷款1元，它们所表达的文本语义都是“贷款”，所以，我们可以忽略掉摘要文本的数字，忽略之后再进行相似度比较。

- 按文本相似度去重：我觉得如果两项摘要，摘要的文本相似度大于90%（现在暂定这个比例，也可以谨慎一点，变成95%），那就可以视为是同一项文本，事实上，这很保险，因为我们是**只在同一个科目组合**下去重，比如如果是这样的：

```text
科目组合：应付账款[借]，银行存款[贷]
摘要：支付分公司货款
科目组合：银行存款[借]，应收账款[贷]
摘要：收分公司货款

这两句摘要的文本相似度很高，但因为它们不在一个科目组合里，所以它们不会被比较被去重
```


## 如何提升准确度？

我们打算引入AI，在当前判断里，我们设计了模型置信度。

就是模型判断的对应该业务活动概率大于80%的，我们认为模型的判断是有力的，所以置信度是高的，如果低于，则是中和低。

我们需要对中和低的部分，去进行检验。

在原版本里，采用的是：程序+模型并行的状态，模型干主要工作，程序负责兜底。

我们现在改成这样：模型干主要工作，AI负责兜底。

核心变化：**我们几乎彻底抛弃了程序**

这个流程应该怎么玩？

- step1 序时账切割：先进行序时账切割，按科目组合进行切割，每个科目组合存储多份摘要，对应多张凭证
- step2 相似摘要去重：在一个科目组合里，可能有摘要是重复的，那么就进行去重
- step3 把“素材”给模型：经过前两步，我们给模型的素材不再是一份完整的序时账，而是经过切割、去重的，这信息里只包含科目科目和对应的摘要，模型根据科目组合和摘要进行判断
- step4 AI去复核模型的判断：模型会给每个科目组合和摘要给出置信度判断，AI负责去复核置信度为“中、低”的部分，让它逐个去复核

>为什么让AI去复核模型的判断？而不让AI完成全部判断？

>其一是经过切割去重后的序时账可能信息还是很多，直接都给AI判断，可能工作量还是会很大，而我们的模型经过这方面的专门训练，它相当于一个滤网，把大部分工作过滤掉，只把小部分小而精的工作留给AI;其二是AI对业务活动的判断可以比肩或者超越我们的模型，AI它有认识文本的能力，它不同于程序，程序是死的，所以AI兜底的效果会更好

- step5 将判断结果写回序时账：经过模型判断、AI复核的结果，写回每一张凭证里

一些注意事项：

### 1. 需要让AI知道应该如何判断

AI虽然很强，能理解文本的含义，但它需要知道我们的规则是怎么玩的。

比如，AI理解了一份文本的含义，它给该文本判断的业务活动为[销售业务活动]，但我们预设的业务桶里，压根没有[销售业务活动]这个业务桶。

我们需要让AI知道我们有哪些业务桶，并让它基于这些业务桶进行判断。

而且，我们可以给AI做出一些指导，或者让AI自己进行积累，比如AI每次判断完它可以把它的判断结果记个笔记，记起来，后面遇到类似的就翻这份笔记，这样AI可以越判断越聪明。

还有，我们可以设定：就让AI去判断置信度中、低的部分，还可以随机抽几个置信度高的给AI判断。

>这有个设计问题：我们要不要让AI去看模型判断的全部？比如序时账经过切割、去重，模型进行了判断，给出了高、中、低置信度。我们可以只把“中、低”的，还有程序自动抽几个“高”的，这部分拿给AI看，这样的话，AI就不用看到全部，而只需要看到它负责兜底的那小部分，这样的设计可以减少token消耗

>再者，我们不要程序自动抽“高”的部分给AI看，而是固定给AI看“中、低”部分，然后写一个脚本放在一边，这个脚本负责抽“高”的部分，抽个5条，AI要抽它就来运行自己运行这个脚本，这个脚本返回5条给AI看

这个形式，最好做成一个SKILL


### 2. 这个skill的框架

既然要做成skill，那这个功能将会蜕变为AI的功能，而不再是人使用的功能。

- AI用的功能：没有必要再streamlit可视化，AI指导用户传入文件，AI输出文件给用户
- 人用的功能：因为人需要操作点击，所以我们原版本才将每一步操作点击可视化了

现在的功能框架需要打碎，变成完全由AI使用的功能。

skill是干嘛的：AI帮忙做序时账清洗

我们怎么写skill.md：我们要给AI写明这个工作流程，告诉它要做的事情，这个skill里AI要做哪些事情：

- 环境准备：帮用户搞定环境，尤其是安装好对应的模型和库
- 上传并配置文件：用户上传文件，AI帮忙配置好对应的字段，当然，程序需要自动检测字段，如果程序检测出了问题，有些字段对不上，AI就帮忙配置一下，这一步一般不用AI出手。在人使用的streamlit版本也是程序自动检测，程序除了问题人就手动调一下。
- 执行序时账清洗：直接按流程走，序时账切割-->去重-->模型判断-->AI兜底，当AI拿到模型判断的结果时，才轮到它干活
- 写回序时账：AI帮忙执行对应的脚本，把结果写回序时账，并将结果给用户，这一步AI就是单纯执行脚本就好了

## 与现版本的架构设计的衔接

现版本，其实也被做成了一个skill

在这个项目的根目录下，就有一个skill.md，但这个skill.md基本是与业务无关的，这个skill是我们特意做的安装skill

这意味着：我们要把序时账清洗这个功能单独独立出来，做成一个单独的skill

但我们也不要动现在的架构，我们在这个项目里创一个新文件夹出来，然后在这个新文件夹里弄新版的序时账清洗。

最后再把这个新文件夹打包作为一个新的单独的skill发布

>现在coding的建议：建议先把“如何去提速”那部分的设计跑通，后面再来考虑引入AI兜底和做成skill的设计，即我们现在只完成前3步，序时账分割、去重和模型判断。
