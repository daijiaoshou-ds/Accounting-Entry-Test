## 2. 桶设计原则

### 2.1 好的关键词

好的关键词应该像**好的搜索词**——能精准命中目标，又不会太窄：

| 好 | 不好 | 原因 |
|----|------|------|
| `差旅` | `北京出差住宿费` | 太具体，覆盖面窄 |
| `社保` | `社会保险费` | 都可以，但 `社保` 更简洁通用 |
| `工资` | `支付` | 太宽泛，会误命中多个场景 |
| `增值税` | `税` | 单字太短，高频噪音 |

### 2.2 关键词选取五条法则

1. **先高频后低频**：优先覆盖出现次数多的词，再补稀有词
2. **有代表性**：选泛化能力强的词（`差旅` 优于 `北京出差`）
3. **避免过拟合**：不要为一次性文本（如某个员工名字）加关键词
4. **允许重叠**：一个词可以属于多个桶，消歧留给下游
5. **保持桶纯净**：每个桶应代表一个连贯的业务概念

### 2.3 什么时候新建桶

满足以下条件时，考虑新建业务桶：

- 聚类 ≥ 5 条未命中记录
- 这些记录有共同的语义主题
- 与现有所有桶无语义重叠
- 代表一个独立的业务类型（不只是一个变体写法）

## 3. 迭代策略

### 3.1 第一轮：粗筛

先用已有的种子桶跑一遍，目标是快速覆盖 60-70%。这一轮会暴露最大的缺口。

### 3.2 第二轮：补大口

看 `聚类建议` 中数量最多的聚类，优先处理高频未命中。通常 2-3 轮就能到 85%+。

### 3.3 第三轮及以后：精细打磨

处理边界情况和中频聚类。这时会出现一些"要不要新建桶"的两难情况——参考第 2.3 节的标准判断。

### 3.4 停止条件

- 命中率 ≥ 90%
- 剩余未命中全是低频噪音（每个聚类 < 3 条）
- 连续两轮没有出现值得建桶的新聚类

## 4. 常见问题排查

### 命中率一直上不去

| 可能原因 | 检查方法 |
|----------|----------|
| 训练数据有空行/格式异常 | 看 `未命中明细` 里文本内容是否为空或乱码 |
| 某一大类业务完全没建桶 | 看 `高频未命中词` 是否反复出现某个主题词汇 |
| 关键词太窄 | 同一个业务的变体写法是否都没命中（如"发薪""付薪""放工资"） |

### 桶太多了怎么办

- 合并语义相同的桶（如"差旅费"和"交通费"可能是一家）
- 只保留出现频率高的桶，低频桶可以合并到大类
- 桶的数量建议控制在 10-20 个，超过 30 个说明粒度太细

### 一条摘要命中多个桶

**这是正常现象，不是 bug。** 当前阶段只做候选匹配，最终归属由下游消歧处理。

例如："支付采购设备款"同时命中"存货采购"和"固定资产"——这是对的，因为确实需要上下文才能判断。

## 5. 配置文件格式规范

### buckets_seed.json

```json
{
  "桶名称": {
    "keywords": ["关键词1", "关键词2", "..."],
    "accounts": ["标准科目1", "标准科目2", "..."]
  }
}
```

- 桶名称：简明业务含义（如"职工薪酬"而非"与职工有关的支出"）
- keywords：字符串数组，一个词可以出现在多个桶中
- accounts：标准一级科目名数组，用于 pattern 科目锚定。**只填标准名称**（如 `材料采购` 而非 `材料采购过渡`），前缀匹配会自动处理公司变体
- JSON 严格格式：双引号、无尾随逗号
