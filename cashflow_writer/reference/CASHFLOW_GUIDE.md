# 现金流量表编制口径

> 这份文件就是**现金流口径的权威说明**，说明程序是怎么把业务分类变成现金流量项目的。
> （它自带完整口径，**不引用仓库里的设计稿**——用户版包里没有 `docs/`。）

---

## 一、三步，全在程序里

```
① 挑凭证   含「银行存款 / 库存现金 / 其他货币资金」的**整张**凭证
              （不是只留货币资金那一行 —— 编现金流要看对方在干什么）
② 定方向   货币资金在借方 = 收现；在贷方 = 付现
③ 定项目   业务桶 → 候选范围 → 按方向筛出唯一一个
              ├─ 剩多个（歧义桶）→ 拿一级科目当裁判
              ├─ 裁判挑不出来     → 用兜底表的默认值
              └─ 这个方向没候选   → 待复核：**方向与桶不符**
```

**项目范围只由业务分类决定**，不需要对方科目列。
一级科目**只在第 ③ 步出现歧义时**才参与，且只用来在已有候选里二选一
—— 它不是一套平行的映射表，详见第三节。

### ⚠️ "全在程序里"不等于"与模型无关"

这三步确实**不调模型、不问 AI**，纯查表、可复现。但**第 ③ 步的输入是模型判出来的桶**：

- 桶对了，映射就对；**桶错了，映射跟着错**；
- 候选唯一时程序**看起来"很确定"**（`现金流判定` 列会写 `桶唯一` / `桶+方向`），
  它不会、也没法报警。真实账（11,456 张凭证）实测 6,667 条货币资金分录里
  **6,241 条（93.6%）**由桶直接定下来，走到科目裁判的只有 13 条。
- 所以**复核改判必须回给程序**：改业务桶要走
  `run --bucket "凭证号=桶"`（应急把手），程序在算现金流**之前**套用，
  现金流按改好的桶重算。**手改导出 Excel 的分类列不会重算现金流**，
  只会让交付物自相矛盾。
- 换句话说：这套映射的**正确性上限，取决于业务分类的正确性**。

### 业务分类从哪来

不是本包算的。**业务桶由 `summary_cleaner`（序时账清洗）判定**：它的模型输出、
四类机械凭证硬约束、费用子桶折叠都在那边完成，本包只接收 `业务分类` 这一列。
这样上游换模型、改桶、改硬约束，本包一行都不用改。

## 二、方向怎么定（最容易搞错的一步）

| 情形 | 方向 | 说明 |
|---|---|---|
| 货币资金行**只有借方**有数 | **收现** | 借方正数、**借方负数都算收现** |
| 货币资金行**只有贷方**有数 | **付现** | 贷方正数、贷方负数都算付现 |
| 同一行借方和贷方都有数 | 无净流量 | 冲销分录，不进现金流量表 |

### 为什么借方负数还是"收现"

理论文档原话：

> 不需要考虑正负号，如果是货币资金借方负数，等于冲收现，而冲收现≠付现。
> 就好比：销售收款 100 万，退货 20 万，在编现金流量时应该是销售收款 80 万，
> 而不能出现销售收款 100 万，采购付款 20 万。

所以方向**看科目在哪一方，不看金额正负**。金额取 `借方 - 贷方`，
红字自然把对应项目冲减：

| 分录 | 方向 | 项目 | 金额 |
|---|---|---|---|
| 借 银行存款 100 | 收现 | 销售商品、提供劳务收到的现金 | +100 |
| 借 银行存款 **-20**（退货红字） | 收现 | 销售商品、提供劳务收到的现金 | **-20** |
| 合计 | | | **+80** ✅ |

如果把红字判成付现，就会得到"收款 100 + 付款 20"两行——这正是文档要避免的。

## 三、业务桶 → 现金流量项目

下表按 `summary_cleaner` 当前的 33 项注册表逐条列出（映射表本体是
`assets/cf/bucket_to_cf.json`，改了桶名要同步改它，否则该桶会全部落到「待复核」）。

| 业务桶 | 收现方向 | 付现方向 |
|---|---|---|
| 销售 | 销售商品、提供劳务收到的现金 | — |
| 采购 | — | 购买商品、接受劳务支付的现金 |
| 薪酬 | — | 支付给职工以及为职工支付的现金 |
| 税费 | 收到的税费返还 | 支付的各项税费 |
| 研发 | — | 支付其他与经营活动有关的现金 |
| 费用 | — | 支付其他与经营活动有关的现金 |
| 费用·能源与场地运营 / 办公与行政运营 / 市场与销售 / 中介与专业服务 / 治理与综合 | — | 支付其他与经营活动有关的现金 |
| 结算手续费 | — | 支付其他与经营活动有关的现金 |
| 政府补助 | 收到其他与经营活动有关的现金 | — |
| 押金保证金 | 收到其他与经营活动有关的现金 | 支付其他与经营活动有关的现金 |
| 员工借支 | 收到其他与经营活动有关的现金 | 支付其他与经营活动有关的现金 |
| 单位往来 | 收到其他与经营活动有关的现金 | 支付其他与经营活动有关的现金 |
| 其他经营收支 | 收到其他与经营活动有关的现金 | 支付其他与经营活动有关的现金 |
| 存款利息 | 收到其他与经营活动有关的现金 | — |
| 投资 ※ | 收回投资收到的现金 / 取得投资收益收到的现金（**歧义，见下**） | 投资支付的现金 |
| 长期资产购建 | — | 购建固定资产、无形资产和其他长期资产支付的现金 |
| 长期资产处置 | 处置固定资产、无形资产和其他长期资产收回的现金净额 | — |
| 权益筹资 | 吸收投资收到的现金 | — |
| 借款 | 取得借款收到的现金 | 偿还债务支付的现金 |
| 利润分配 | — | 分配股利、利润或偿付利息支付的现金 |
| 利息支出 | — | 分配股利、利润或偿付利息支付的现金 |
| 筹资费用 | — | 支付其他与筹资活动有关的现金 |
| **折旧摊销** | 不产生现金流量（非付现） | |
| **成本结转** | 不产生现金流量（销售出库结转成本，无货币资金） | |
| **生产制造** | 不产生现金流量（领料/结转，无货币资金） | |
| **期末结转** | 不产生现金流量（损益结转） | |
| **资金内部往来** | 不产生现金流量（货币资金互转，总额不变） | |
| **汇兑损益** | 汇率变动对现金的影响（**中性项目**，不分收付方向） | |

「—」= 该方向**没有候选**。不是"暂时没配"，是**按定义不该出现**，见下。

> **设计原则**
>
> 1. **单向桶只列一个方向**：桶名自带方向的（销售 / 采购 / 薪酬 / 研发 / 费用 /
>    政府补助 / 利润分配 / 长期资产购建 / 长期资产处置 / 权益筹资），只列那一个方向。
> 2. **无方向的桶两个方向都列**：桶名只说"什么事"的（税费 / 往来 / 借款 /
>    押金保证金 / 投资 / 利息），收付都可能；漏了反向项目，
>    "退款 / 赎回 / 返还"这类凭证就永远判不出来。
> 3. **一个桶在同一方向上尽量只有一个**项目。能靠桶定义避免的二义性，
>    就不该推给用户。

### 为什么单向桶**不能**给反方向候选

候选表是**无方向**的，方向由货币资金借贷方筛。如果"销售"里挂着
"支付其他与经营活动有关的现金"，那么一张**付款**凭证被判成销售时，
程序会**顺着方向**挑出"支付其他…"——一个错桶就这样被洗成一个看起来
合理的现金流项目，错误被彻底掩盖，而且报表是平的，谁也不会发现。

所以反方向候选一律**不给**，让它落到「待复核 · 方向与桶不符」，
逼着回去复核**业务分类**，而不是在现金流层糊过去。

**退款 / 退回也一样**：收到一笔"销售退款"说明这笔不是销售收款，
多半该归 `单位往来` / `其他经营收支`，而不是给"销售"配一个付款项目。

### 汇兑损益：不是"没有现金流"，而是不归收付两侧

汇兑损益在报表里**单独一行**（"汇率变动对现金的影响"），既不进经营活动，
也不进投资/筹资活动。所以它的项目方向标为**中性**：桶定了就是它，
不看借贷方向。报表汇总时会归到「其他」，并计入"现金及现金等价物净增加额"。

> ⚠️ 已知口径问题：结汇/购汇（外币户 ↔ 人民币户）本质是**货币资金内部划转**，
> 现有桶会把它判进「汇兑损益」并计入"汇率变动对现金的影响"，金额可能被放大。
> 真账上出现过 8,185,043 / 8,051,000 两行（净额 13 万）。要不要在现金流层
> 把"结汇/收汇/购汇"摘要且两边都是货币资金的凭证按"无现金流量"处理，
> **留给下一轮口径讨论**。

### 投资：一个真正的歧义桶（靠一级科目当裁判）

`投资` 在**收现**方向上有**两个**候选，分属不同业务含义：

| 候选 | 什么情况下是它 |
|---|---|
| 收回投资收到的现金 | 赎回理财、处置股权、定期存款到期 |
| 取得投资收益收到的现金 | 收到理财分红、子公司分红、利息收益 |

> 「取得投资收益收到的现金」是 **2026-10 用户口径**加进来的：
> 以前它不在候选里，"收到理财分红收益"这类业务**从候选里挑哪个都错**，
> 只能靠 `--cf` 手工指定。
> **已知代价**：赎回理财**同时带收益**的凭证会命中 2 个候选（本金 + 收益）→ 落
> 「待复核」。用户明确接受这个代价 —— 一张凭证只有一条货币资金行，只能给一个项目，
> 判不了就交人工，比洗成一个错项目好。

桶层面**分不出来**——根因是桶没拆开（金融产品投资 / 投资收益）。当前不重训模型，
所以加一层**歧义裁判**：

```
业务桶定候选 → 方向筛 → 仍剩多个 → 才拿一级科目当裁判
```

| 一级科目 | 裁判结果 |
|---|---|
| 交易性金融资产、债权投资、其他债权投资、其他权益工具投资、持有至到期投资、可供出售金融资产、长期股权投资、投资性房地产、定期存款、大额存单、结构性存款、理财产品 | 收回投资收到的现金 |
| 投资收益、应收股利、应收利息 | 取得投资收益收到的现金 |
| 实收资本、资本公积、股本 | 吸收投资收到的现金（`权益筹资` 桶已直接覆盖，裁判表保留兼容旧桶） |

**裁判表在哪里**：`assets/cf/account_ruling.json`

> **赎回带收益怎么处理**（命中 2 个候选 → 待复核）：
> 看摘要与金额主体 —— 以本金为主（收益占比很小、摘要只写"赎回"）→ 用
> `--cf "行号=收回投资收到的现金"`；收益是单独一笔（摘要写"分红/利息"）→
> 通常压根不会命中两个（科目里只有投资收益）。
> **两条都说不清时保留「待复核」**，别猜：这是设计要你去问人的地方。

### 利息支出：只有一条路

`利息支出` 桶在付现方向只有一个候选（分配股利、利润或偿付利息支付的现金），
不再歧义——**银行手续费已经从「利息支出」里拆出去，成为独立的
`结算手续费` 桶**（付现 → 支付其他与经营活动有关的现金）。
旧版靠"裁判 + 兜底"区分利息与手续费的那套已经不需要了。

**兜底表在哪里**：`assets/cf/account_ruling.json` 的 `fallback` 字段
（目前只剩旧 18 桶体系的一条兼容项，新桶体系用不到）。

### ⚠️ 一级科目只当裁判，绝不当前锋

依赖顺序是**严格**的：

```
① 业务桶定候选        ← 唯一的主依据
② 货币资金借贷定方向
③ 只有 ①② 还定不下来，才问一级科目
④ 裁判也挑不出来，才用兜底表的默认值
```

绝大多数凭证在第 ② 步就出结果了；只有"歧义桶 + 对应方向"那**一小撮**会走到第 ③④ 步。
判定来源（结果文件「业务分类结果」sheet 的「现金流判定」列）会明确标出：

| 判定来源 | 含义 |
|---|---|
| 桶唯一 | 桶只有一个项目，直接定 |
| 桶+方向 | 桶有多个项目，按方向筛出唯一一个 |
| **科目裁判** | 桶 + 方向仍歧义，由一级科目定夺 |
| **桶兜底** | 裁判挑不出来，用兜底表的默认值 |
| **中性项目** | 不归收付两侧（汇兑损益 → 汇率变动对现金的影响） |
| **待复核** | 定不下来：方向与桶不符 / 科目没登记 / 科目也重叠 |
| **未分类** | 业务桶不在映射表里（桶名不认识），不能当成"不影响现金流" |
| 无现金流量 | 该桶本就不产生现金流（折旧摊销 / 成本结转 / 资金内部往来） |
| 冲销无净流量 | 同一行借贷双方都有数 |
| 补丁补充 | 由 `--cf` / `--cf-patch` 人工/AI 补上的 |

**为什么不让一级科目当主映射表**：那等于两套口径并行。桶口径一变，
这套表就成了补丁摞补丁，越补越乱，而且没人说得清最终以谁为准。

### 歧义桶出现 = 该拆桶了

歧义桶是个**信号**，不是常态。它说明业务桶的粒度不够：

- `投资` 把"金融产品投资"和"投资收益"混在一个桶里。

正确解法是**把桶拆开**，然后重训模型。裁判表和兜底表都是**过渡补丁**：
当某类歧义频繁出现时，说明该回去拆桶重训了，而不是继续往里加科目。

## 四、判不下来时怎么办：标"待复核"，不硬选

程序会把这些条目放进 `run` 出参的 **`cashflow_review`**，
而不是硬选一个（**不落 Excel 的独立 sheet**——待复核是给 AI 的工作项，
但交付 Excel 里能筛出来，见下面的「列取值」）：

| # | 情况 | 怎么办 |
|---|---|---|
| 1 | **方向与桶不符**（单向桶遇到反方向凭证） | 先复核**业务分类**（多半该是 `单位往来` / `其他经营收支`）；确属退款等，再 `--cf` 直接指定项目 |
| 2 | 歧义桶，但一级科目没登记在裁判表里 | 看科目/摘要 → `--cf`；同类反复出现就往 `account_ruling.json` 补科目 |
| 3 | 一级科目同时命中多个候选 | 同上（科目本身也重叠，裁判失效） |
| 4 | 业务桶不在映射表里（未分类） | 先复核业务分类；确实是桶名变了就补 `bucket_to_cf.json` |

**每条都带 `凭证号` / `业务分类` / `业务分类置信度`**，所以第 1~2 类可以先判断
"是不是桶判错了"；`cashflow_review_by_voucher` 把同一凭证的多条并成一行
（一屏能看完）。

### 交付 Excel 里怎么认出"待人工"的行

| 列 | 取值 | 说明 |
|---|---|---|
| `现金流判定` | `桶唯一` / `桶+方向` / `科目裁判` / `桶兜底` / `中性项目` / `补丁补充` / `无现金流量` / `冲销无净流量` / `待复核` / `未分类` | 项目是**怎么定出来的**；空 = 这一行不是货币资金行 |
| `现金流复核` | `需复核` / 空 | **只有程序判不下来的行才写「需复核」** —— 让用户就筛这一列 |

> 真账实测（64,255 行 / 11,456 张凭证 / 6,667 条货币资金分录）：
> **桶唯一 6,084 / 桶+方向 157 / 中性项目 162 / 无现金流量 177 / 待复核 74 /
> 科目裁判 13**，`未分类` 与 `冲销无净流量` 各 0 条。
> 待复核占 1.1%；`by_source` 的分布与这两个口径完全对得上。
> 出参里的 `cashflow.by_source` 就是这个分布，`cashflow.rows_without_item_detail`
> 是那批空项目行的拆分。
>
> 8 家公司的合成大账（846,991 行 / 144,119 张凭证 / 67,826 条分录）上是：
> 桶唯一 61,479 / 无现金流量 2,687 / 桶+方向 1,854 / 待复核 1,073（1.6%）/
> 中性项目 619 / 科目裁判 113 / 冲销 1。**离群公司越多，待复核比例越高**，
> 因为桶的边界是按单一公司口径调的。

**第 1 种会出现在正常数据里**（模型难免把个别凭证判进单向桶的反方向）：
这本账里 74 条待复核中，绝大多数是"费用/薪酬 收现"（退款、工资退回）与
"投资 收现命中两个候选"。这不是故障，是程序在**报告模型判错了**——
它比"报表平但项目错"安全得多。

**结论只能靠补丁交回程序**——产出 Excel 永远由程序落盘，AI 不手改产出文件。
两条路任选：

```cmd
:: ① 命令行直接给（AI 首选：不写文件、可重复、一次交完）
%PY% -X utf8 cli.py run "序时账.xlsx" --cf "502=吸收投资收到的现金"

:: ② 补丁文件（人工长期维护）
%PY% -X utf8 cli.py run "序时账.xlsx" --cf-patch "补丁.json"
```

被采纳的条目在结果里标为「补丁补充」，可追溯、可复现。
**合法现金流量项目名的权威清单是 `assets/cf/cf_items.json`**：
程序给的 `候选项目` 为空、或看着不对（例如"理财分红收益"该进
`取得投资收益收到的现金` 而候选里没有），就查这份清单，
再用 `--cf` 直接指定——**不必从候选里挑**。

理由与清洗侧删掉程序打分一致：**没有可靠依据时硬选一个，比标出来更危险**。

## 五、当前边界（还没做 / 已知限制）

| 项 | 状态 |
|---|---|
| 正式现金流量表（要货币资金期初余额、表内勾稽） | **未做**——目前只出"按项目聚合 + 净增加额" |
| 汇率变动对现金的影响 | 由「汇兑损益」桶出（中性项目）；**只覆盖凭证里能看到的汇兑调整**。结汇/购汇是否该算作内部划转，待定 |
| 同一项目跨月/跨凭证的净额抵减 | 靠金额正负号天然完成（见第二节） |
| 非经营性往来的收付抵销（净额列示） | 未做 |
| **`投资` 桶的固有歧义** | 收现 2 个候选（收回投资 / 取得投资收益），靠一级科目当裁判过渡；根治要拆桶重训 |
| **赎回理财同时带收益** | 本金科目 + 收益科目同时出现 → 命中 2 个候选 → 待复核（用户 2026-10 确认接受这个代价） |
| 直接支付的利息（借 `财务费用`，不经 `应付利息`） | 若桶判成 `利息支出` 就走"分配股利、利润或偿付利息"；判成 `结算手续费` 就走"支付其他…"。**桶决定结果**，所以桶的边界要清楚 |
| `生产制造` 桶 | 映射为"不产生现金流量"。真账里若存在"付现采购直接记生产成本"的凭证，会被静默当成无现金流——**下一轮口径讨论项** |

## 六、自检

```cmd
%PY% -X utf8 cli.py validate
```

| 字段 | 期望 | 含义 |
|---|---|---|
| `problem_count` | `0` | 引用了不存在的项目 / 方向非法 / 兜底表写错 |
| `ambiguous_buckets` | 看内容 | 哪些桶在哪个方向上有歧义，`ruled` / `fallback` 是否已覆盖 |
| `ruling_items` | 与 `ambiguous_buckets` 对应 | 裁判表登记的项目 |
| `fallback_items` | 与 `ambiguous_buckets` 对应 | 兜底表登记的组合 |
| `ruling_idle` | **空** | 登记了但实际用不到的裁判条目 → 应删除 |
| `ambiguous_without_ruling` | **空** | 有歧义、既没裁判也没兜底的候选 → 会全部落到待复核 |
| `one_way_buckets` | 看内容 | 单向桶（列表越长越正常，见第三节） |

`status` 里也有同一份自检的摘要（`cf_maps.validate_problems`）。

映射表是**手工维护的 JSON，JSON 即权威**（`assets/cf/*.json`）。改完跑一次
`validate` 就能发现矛盾：项目名写错、兜底值不在候选里、桶名拼错都会报出来。
